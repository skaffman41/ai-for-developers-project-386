**Дата проверки официальных источников:** 2026-11-07.

## Problem Statement

У проекта «Календарь звонков» описаны сценарии владельца календаря и гостя, но пока нет исполняемого приложения и собственных проверок кода. Разработчик не может воспроизводимо запустить frontend и backend, проверить изменения одной командой и получить такой же результат в GitHub Actions.

В репозитории есть документация и предоставленный Hexlet workflow. Он запускает внешнюю проверку Hexlet и не содержит команд проверки будущего приложения.

## Solution

Подготовить минимальное приложение с React frontend и Fastify backend, единым управлением инструментами и задачами через mise. После подготовки окружения одна команда запускает обе части, другая выполняет все проверки. Vitest проверяет запуск собранного приложения через настоящий HTTP. GitHub Actions выполняет ту же команду проверок при каждом push в отдельном workflow.

Frontend показывает заголовок «Календарь звонков» и подпись «Каркас приложения». Backend предоставляет технический endpoint состояния. Типы встреч, доступность и бронирования на этом этапе не реализуются.

## User Stories

1. Как разработчик, я хочу установить одинаковые версии инструментов из репозитория, чтобы локальное окружение соответствовало CI.
2. Как новый участник, я хочу получить понятную инструкцию подготовки чистого клона, чтобы запустить проект без догадок.
3. Как разработчик, я хочу установить зависимости одной командой из корня, чтобы не обслуживать отдельные установки frontend и backend.
4. Как разработчик, я хочу запустить обе части одной командой, чтобы сразу приступить к работе.
5. Как разработчик, я хочу запускать frontend и backend по отдельности, чтобы исследовать каждую часть независимо.
6. Как посетитель, я хочу увидеть страницу «Календарь звонков», чтобы убедиться, что frontend работает.
7. Как разработчик, я хочу получить успешный ответ endpoint состояния, чтобы проверить доступность backend.
8. Как разработчик, я хочу останавливать запущенные части через Ctrl+C, чтобы освобождались процессы и порты.
9. Как разработчик, я хочу получать понятную ошибку при занятом порте, чтобы не проверять случайно другой процесс.
10. Как разработчик, я хочу собирать frontend и backend, чтобы проверять пригодность исходников к запуску после сборки.
11. Как разработчик, я хочу отдельно запускать проверку типов, чтобы ошибки TypeScript обнаруживались до выполнения приложения.
12. Как разработчик, я хочу отдельно запускать линтер, чтобы находить ошибки в исходниках и конфигурации.
13. Как разработчик, я хочу проверять и исправлять форматирование отдельными командами, чтобы проверки не меняли файлы незаметно.
14. Как разработчик, я хочу запускать smoke-тест без предварительно запущенных серверов, чтобы результат не зависел от моего рабочего сеанса.
15. Как сопровождающий, я хочу проверять реальные HTTP-ответы запущенных процессов, чтобы выявлять ошибки запуска и сборки.
16. Как разработчик, я хочу выполнять все проверки одной командой, чтобы не пропускать обязательные шаги.
17. Как сопровождающий, я хочу видеть результат этих проверок на каждом push, чтобы контролировать состояние любой ветки.
18. Как участник учебного проекта, я хочу сохранить предоставленную проверку Hexlet, чтобы продолжать проходить проверки курса.
19. Как разработчик, я хочу установить локальные Git-хуки с теми же проверками качества, чтобы обнаруживать ошибки перед коммитом.
20. Как агент, я хочу найти команды и правило Conventional Commits в корневых инструкциях, чтобы работать по соглашениям проекта.
21. Как сопровождающий, я хочу сохранить документацию пользовательских сценариев, чтобы каркас не менял требования к будущим бронированиям.

## Implementation Decisions

Решения согласованы с уточнениями пользователя, приведёнными ниже и в Comments.

- Инфраструктура ограничивается необходимым для требований Hexlet: два приложения, общие команды, smoke-тест, проверки качества, локальный hook и один дополнительный workflow. Использовать штатные возможности выбранных инструментов; не добавлять собственную платформу оркестрации, bootstrap framework, контейнеры, CI-матрицы, coverage gates и дополнительные сервисы. Небольшие вспомогательные функции допустимы, если без них нельзя надёжно запустить и завершить процессы.
- Один приватный npm workspace с двумя приватными пакетами: frontend и backend. Одна установка зависимостей и один общий npm lockfile; дополнительные менеджеры пакетов и монорепозиторные платформы не нужны. Это стандартная модель [npm workspaces](https://docs.npmjs.com/cli/v11/using-npm/workspaces/).
- Frontend: клиентское React-приложение на TypeScript и Vite с официальным React-плагином. Использовать минимальную основу официального шаблона React + TypeScript, убрав демонстрационные счётчики и логотипы. Такой учебный старт описан в [React](https://react.dev/learn/build-a-react-app-from-scratch/) и [Vite Getting Started](https://vite.dev/guide/).
- Backend: Fastify на TypeScript. Создание приложения отделено от запуска HTTP listener; ошибка запуска даёт ненулевой код выхода, сигналы завершения закрывают сервер. Базовый запуск и ESM описаны в [Fastify Getting Started](https://fastify.dev/docs/latest/Guides/Getting-Started/), компиляция TypeScript — в [официальном руководстве](https://fastify.dev/docs/latest/Reference/TypeScript/).
- Обе части используют ESM и строгую проверку TypeScript. Для frontend используется разрешение модулей Bundler, для backend — NodeNext. В разработке backend запускается Node в режиме watch с поддерживаемым удалением типов; сборка выполняется tsc, собранный backend запускается обычным Node. Для backend включить erasableSyntaxOnly, verbatimModuleSyntax и переписывание относительных расширений при сборке; не использовать enum, parameter properties и aliases, требующие преобразования. Node не проверяет типы, поэтому typecheck обязателен. Эти ограничения следуют из [документации выбранного Node 24](https://nodejs.org/docs/latest-v24.x/api/typescript.html).
- Минимальная страница frontend не обращается к backend. Для этого этапа не требуются CORS, API proxy, роутер, state manager или библиотека запросов.
- Единственный обязательный API-контракт: GET /health без авторизации и тела запроса возвращает HTTP 200, Content-Type application/json с допустимым charset и JSON-объект с единственным полем status со значением строки ok. Endpoint не обращается к БД и внешним сервисам.
- Локальные адреса по умолчанию: frontend http://127.0.0.1:5173, backend http://127.0.0.1:3000; просмотр frontend после сборки — http://127.0.0.1:4173. Для backend документируются HOST и PORT; запуск без переменных окружения работает. Занятый явно выбранный порт вызывает ошибку вместо незаметного переключения.
- mise управляет Node, hk и общими задачами. npm берётся из зафиксированного дистрибутива Node. npm-пакеты приложения и инструменты JavaScript устанавливаются локально через npm, без дублирования их установки через mise.
- Все задачи доступны из корня через mise run. Команда dev запускает обе части параллельно и завершает их при Ctrl+C или ошибке запуска одной из них. У build есть явная зависимость перед smoke-тестом: порядок элементов в depends сам по себе последовательность не гарантирует, что отмечено в [mise Tasks](https://mise.jdx.dev/tasks/).
- ESLint использует flat config, recommended-правила JavaScript и typescript-eslint для TS/TSX. Prettier отвечает за форматирование; eslint-config-prettier отключает конфликтующие правила. Конфигурация учитывает browser globals отдельно от Node globals. Основа — [typescript-eslint Quickstart](https://typescript-eslint.io/getting-started/) и [интеграция Prettier с линтерами](https://prettier.io/docs/integrating-with-linters).
- Проверки линтера, форматирования и типов охватывают исходники обеих частей, тесты и применимые конфигурации. Генерируемые результаты и зависимости исключаются. Защищённый workflow Hexlet исключается из форматирования и любых автоисправлений.
- hk предоставляет локальный pre-commit hook с проверками линтера и форматирования через общие задачи mise. Hook только проверяет: не исправляет, не добавляет файлы в индекс и не создаёт коммиты. Его установка отдельным шагом относится к текущему клону; глобальная Git-конфигурация не меняется. Pkl CLI отдельно не требуется в выбранной версии hk. Основа — [hk Getting Started](https://hk.jdx.dev/getting_started.html).
- Будущий отдельный GitHub Actions workflow запускает ту же команду check на каждый push веток и тегов без фильтра по путям и выбранной ветке. Он использует Ubuntu 24.04, checkout, зафиксированную версию mise, locked-установку инструментов и npm ci. Actions фиксируются полными commit SHA с комментарием версии; конкретные SHA проверяются при реализации. Для установки mise используется официальный [mise-action](https://github.com/jdx/mise-action); общий порядок описан в [mise CI](https://mise.jdx.dev/continuous-integration.html). Проверкам приложения не нужны секреты Hexlet.
- Корневые инструкции агента и README дополняются командами подготовки, запуска, тестов, линтера и всех проверок. В инструкции агента добавляется правило Conventional Commits: type(scope): description, где scope необязателен; например, feat: add application skeleton и docs: describe development commands. Существующие проектные инструкции сохраняются; личные предпочтения пользователя в общие документы не переносятся.

К прямым вспомогательным зависимостям относятся `@types/node` ветки 24, `@types/react` и `@types/react-dom` ветки 19, `@eslint/js` и `globals`. Точные опубликованные версии всего вспомогательного набора нужно подтвердить в задаче 01 до подготовки установки. Дополнительные React-плагины линтера, React Compiler, DOM environment и coverage-пакеты для согласованного каркаса не требуются.

Обязательный порядок перед установкой:

1. Проверить существование точных версий в npm registry и официальных релизах, фактические engines и peerDependencies, включая React/React DOM, типы и вспомогательные конфигурационные пакеты. Проверить наличие mise и hk для macOS arm64 и Linux x64 и соответствие версии npm выбранному Node.
2. Зафиксировать проверенный набор и источники в результате первой задачи декомпозиции. Если публикации или ограничения расходятся с таблицей, подобрать минимальную совместимую корректировку в рамках согласованного стека и обновить спецификацию до установки.
3. После подготовки manifests и выбранного окружения выполнить разрешение полного дерева через npm install --dry-run --ignore-scripts --package-lock=false --strict-peer-deps --engine-strict --no-audit --no-fund. Эта проверка предшествует первой фактической установке и созданию npm lockfile; ошибок engines и peerDependencies быть не должно. Не использовать force или legacy-peer-deps для обхода несовместимости.
4. Только после успешной проверки установить зависимости, сохранить точные версии и lockfile и подтвердить связку сборкой и smoke-тестом. Эти действия относятся к будущей реализации задач.

Правила воспроизводимости:

- В конфигурации mise фиксируются полные версии Node и hk. Общий mise lockfile содержит записи как минимум для macos-arm64 и linux-x64; установка выполняется через mise install --locked. Это предусмотрено [документацией lockfile](https://mise.jdx.dev/dev-tools/mise-lock.html).
- Версия самого mise фиксируется отдельно в инструкции установки и CI; setup проверяет ожидаемую версию. Один только min_version не считается фиксацией версии mise.
- У npm фиксируется packageManager npm@11.19.1, а проверка окружения отклоняет несовпадение ожидаемых версий Node/npm. Глобальное обновление npm не требуется.
- Все внешние прямые npm-зависимости, включая вспомогательные типы и конфигурационные пакеты, сохраняются точными версиями без latest, ^ и ~. Для типов Node выбирается ветка 24, для React — 19. Совместимые точные версии вспомогательных пакетов подтверждаются в задаче 01 до установки; задача 02 переносит их в manifests и фиксирует разрешённое дерево в lockfile после успешного dry-run.
- Общий npm lockfile коммитится. Для чистого клона и CI используется npm ci: при расхождении с manifest установка завершается ошибкой, lockfile не переписывается. Это поведение описано в [npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci/).
- Конфигурационные импорты hk фиксируются на той же версии, что бинарный hk. Незафиксированные вызовы npx и генераторов в повседневных командах и CI не допускаются. Если генератор Vite используется однократно при реализации, его точная версия записывается в результат задачи; зависимости шаблона приводятся к согласованному набору.

## Project Structure

Целевая структура после будущей реализации. Сейчас создаются только спецификация и задачи; перечисленные файлы приложения, конфигурации и CI пока не создаются. Структура задаёт разделение ответственности; небольшие конфигурации можно объединить, если это упрощает каркас и сохраняет критерии приёмки.

## Testing Decisions

- Граница проверки — публичный HTTP-интерфейс самостоятельно запущенного собранного приложения. Минимум один smoke-сценарий охватывает оба процесса; эта граница согласована пользователем.
- Vitest работает в Node environment и использует настоящий HTTP-клиент. Тест запускает собранный backend и Vite preview собранного frontend дочерними процессами. Подмена HTTP моками и Fastify inject не подтверждает запуск listener и не заменяет этот smoke-тест.
- Проверяются HTTP 200 и JSON-контракт GET /health. Для frontend проверяются HTTP 200, HTML Content-Type, наличие корневого элемента React и успешная загрузка указанного в HTML JS-ресурса с подходящим Content-Type. Возврат SPA HTML вместо JS не считается успехом.
- Серверы запускаются на изолированных свободных loopback-портах; тест отслеживает именно свои процессы и их раннее завершение. Готовность проверяется ограниченным по времени polling, без безусловного долгого sleep. Общий предел ожидания готовности — 30 секунд, отдельного HTTP-запроса — 5 секунд; ошибка включает адрес и вывод процесса.
- Процессы и соединения закрываются и при успешном выполнении, и при ошибке. Тест не использует уже запущенные dev-серверы и не завершает чужие процессы. Повторный запуск не оставляет занятых портов. Отсутствие найденных тестов считается ошибкой.
- Проверяются внешние результаты запуска и HTTP-контракты. Снимки внутренней структуры React, тесты конфигурационных объектов и обязательный процент покрытия не нужны. Предыдущих тестов в репозитории нет.
- HTTP smoke не доказывает отрисовку React в браузере. При приёмке вручную открывается frontend и проверяются заголовок, подпись и отсутствие ошибок запуска в консоли. Browser automation и отдельные компонентные тесты на этом этапе не добавляются.
- При реализации вручную проверяются ненулевые коды при ошибке линтера, форматирования, типов и smoke, а также остановка dev через Ctrl+C. Для этого временные изменения не коммитятся. Новые автоматические тесты сверх явно запрошенного smoke требуют отдельного запроса пользователя.
- Для приёмки CI достаточно успешного запуска GitHub Actions после push. Искусственно падающий запуск CI не требуется, если локально уже зафиксированы ненулевые коды обязательных проверок при нарушениях. Commit и push в рамках текущего запроса не выполняются.

## Acceptance Criteria

- [ ] AC-01. В чистом клоне на macOS arm64 и в CI на Linux x64 подготовка по README устанавливает согласованные версии без неописанных глобальных JS-пакетов; npm ci не изменяет lockfile.
- [ ] AC-02. mise run dev из корня запускает frontend и backend. Страница на 127.0.0.1:5173 показывает «Календарь звонков» и «Каркас приложения»; ошибок запуска в браузерной консоли нет.
- [ ] AC-03. GET http://127.0.0.1:3000/health возвращает HTTP 200 и заданный JSON-контракт. БД, ключи и внешние сервисы для этого не требуются.
- [ ] AC-04. Обе части запускаются по отдельности; занятый выбранный порт даёт явную ошибку. После Ctrl+C общего запуска оба процесса завершены и порты освобождены.
- [ ] AC-05. mise run build создаёт результаты обеих частей; команды start:backend и preview:frontend запускают их после сборки.
- [ ] AC-06. mise run test самостоятельно собирает приложение и выполняет хотя бы один smoke-тест настоящего запуска обеих частей с успешными HTTP-ответами и проверкой /health. Нулевой набор тестов не проходит.
- [ ] AC-07. При неготовности или раннем завершении процесса smoke падает с диагностикой за ограниченное время. После успешного и неуспешного запуска принадлежащие тесту процессы завершаются.
- [ ] AC-08. Отдельно работают lint, format:check и typecheck; их нарушения дают ненулевой код. Проверки охватывают обе части, тесты и применимую конфигурацию.

- [ ] AC-11. .github/workflows/hexlet-check.yml остаётся побайтово прежним, не удаляется и не переименовывается. Никакая команда форматирования или hook его не меняет.
