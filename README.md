Разработайте совместно с ИИ сервис для бронирования календаря

Учебный проект Хекслета: https://ru.hexlet.io/programs/ai-for-developers
Как это должно работать: https://files.hexlet.app/a/2ipc5m

## Пользовательские сценарии

В сервисе один заранее заданный владелец календаря. Гости записываются на встречи без регистрации.

### Владелец календаря

1. Открывает отдельный раздел управления без входа и проверки прав.
2. Создаёт тип встречи: указывает обязательные название и длительность в целых положительных минутах. Описание необязательно.
3. Просматривает типы встреч и список бронирований: тип встречи, дату, время, имя и email гостя.

### Гость

1. Выбирает тип встречи.
2. Выбирает дату и свободный слот в календаре.
3. Вводит обязательные имя и email и подтверждает бронирование.
4. Получает подтверждение на экране с типом встречи, датой, временем и часовым поясом. Письма не отправляются.

Если свободных слотов нет, гость выбирает другую дату или тип встречи.

Если выбранный интервал успели забронировать, гость видит алерт «Слот уже занят». После закрытия алерта список слотов обновляется, а введённые имя и email сохраняются для повторной попытки. При одновременных попытках подтверждается только одна бронь.

### Правила доступности

- Все даты и время рассчитываются и отображаются в часовом поясе `Europe/Moscow`.
- Календарь показывает сегодня и следующие 13 календарных дней. Рабочее время — понедельник–пятница, 09:00–18:00; выходные недоступны.
- Допустимые начала встреч идут с шагом 30 минут от 09:00. Длительность фиксирована у типа встречи и не обязана быть кратной 30 минутам.
- При проверке доступности учитывается полный интервал встречи: начало строго позже текущего времени, окончание не позже 18:00, пересечений с существующими бронированиями нет.
- Занятость общая для всех типов встреч. Любое пересечение запрещено, но следующая встреча может начинаться сразу после окончания предыдущей.

В первую версию не входят редактирование и удаление типов встреч, отмена и перенос бронирований, авторизация, интеграции с внешними календарями и уведомления.

## Стек

- Frontend: React 19.3.1, TypeScript 6.0.3, Vite 8.3.6.
- Backend: Fastify 5.12.8, TypeScript, ESM; Node запускает TypeScript в разработке, после сборки — JavaScript.
- Проверки: Vitest 5.1.0, Playwright 1.65.0 (Chromium), ESLint 10.14.0, typescript-eslint 8.72.1, Prettier 3.9.10.
- Приватные npm workspaces `contract`, `frontend` и `backend`, один корневой `package-lock.json`.
- mise 2026.11.3 управляет Node 24.22.2, встроенным npm 11.19.1, hk 2.11.1 и GitHub CLI 2.103.3. Точные версии JS-зависимостей указаны в manifests.

## Установка

Поддерживаемые окружения: macOS arm64 и Linux x64. Нужны Git и curl.
Установите точную версию mise по [официальной инструкции](https://mise.jdx.dev/installing-mise.html):

```bash
curl --fail --silent --show-error --location https://mise.run | MISE_VERSION=v2026.11.3 sh
export PATH="$HOME/.local/bin:$PATH"
mise --version
```

Добавьте `~/.local/bin` в `PATH` своего shell для следующих сеансов. Подготовьте проект из корня:

```bash
git clone https://github.com/skaffman41/ai-for-developers-project-386.git
cd ai-for-developers-project-386
mise trust
mise install --locked
mise run setup
mise run browser:install
```

На Linux используйте `mise run browser:install -- --with-deps`: Playwright установит
также системные библиотеки Chromium (для этого могут понадобиться права sudo).
Команда загружает браузер, соответствующий закреплённой версии Playwright; повторите её
после обновления Playwright. [Официальный registry](https://registry.npmjs.org/@playwright/test/1.65.0)
указывает Node `>=20`, совместимый с Node 24 проекта. Подготовка браузера следует
[инструкции Playwright](https://playwright.dev/docs/browsers#install-browsers).

`mise.lock` фиксирует Node, hk и gh с контрольными суммами для обеих платформ.
`setup` проверяет точные версии mise, Node и npm, выполняет `npm ci`, затем `hooks:install`.
Хук hk устанавливается только для текущего клона через `hk install --mise`; глобальная Git-конфигурация не меняется.
Отдельный Pkl CLI не нужен: hk использует встроенный evaluator.
Отдельный сервер БД, глобальные JS-пакеты, ключи и внешние сервисы для запуска не нужны.
SQLite встроен в Node; постоянный файл нужно явно подготовить по инструкции ниже.
Для первой установки инструментов, npm-зависимостей и Chromium нужен доступ к источникам загрузки.

## Использование

Все команды выполняются из корня:

Сначала выберите постоянный локальный каталог вне временных файлов, зависимостей и
результатов сборки. Файл и соседние SQLite journals должны оставаться на том же
исправном диске при перезапуске и пересборке. Пример для локальной разработки:

```bash
mkdir -p "$HOME/.local/share/call-calendar"
export DATABASE_PATH="$HOME/.local/share/call-calendar/calendar.sqlite"
mise run db:prepare
mise run dev
```

`db:prepare` один раз создаёт **пустую** БД без демонстрационных данных; существующий
файл не заменяет. При следующих запусках достаточно задать тот же абсолютный
`DATABASE_PATH` и выполнить `mise run dev`. Каталог должен существовать и допускать
запись файла и rollback journal. Не используйте сетевой диск, `/tmp`, `node_modules`
или `dist`; тесты используют свои временные файлы, а данные разработчика не трогают.

Обычный запуск открывает только существующую БД (`mode=rw`), проверяет приложение,
версию/структуру схемы и целостность. Отсутствующий, недоступный, повреждённый или
чужой файл останавливает backend до HTTP. Подмены пустым файлом или памятью нет.
Подготовка схемы/версии — одна транзакция. Текущая версия — 3. Версия 1 транзакционно получает таблицу результатов попыток
(v2), затем таблицу бронирований для чтения занятости (v3); версия 2 получает только
миграцию бронирований. Типы и сохранённые результаты попыток сохраняются. Ошибка откатывает изменение схемы и версии. Чужие и будущие версии
отклоняются без сброса. Сохраняются `journal_mode=DELETE`,
`synchronous=EXTRA`, `foreign_keys=ON`, ожидание блокировки до 5000 мс; на macOS —
`fullfsync=ON`. Гарантия сохранности предполагает исправные диск, файловую систему
и синхронизацию ОС; автоматическое резервное копирование не входит в эту версию.

Откройте http://127.0.0.1:5173: главная объясняет запись на встречу без регистрации.
Ссылка «Записаться на встречу» открывает `/booking` с реальным списком типов встреч:
название, длительность, описание и устойчивое обозначение. Новые типы идут первыми;
на пустой БД доступно обновление списка. Загрузка, ошибка и повтор показаны отдельно.
После выбора типа кнопка «Выбрать дату и время» открывает московский календарь:
сегодня и следующие 13 дней, будни 09:00–18:00. Полные свободные интервалы учитывают
длительность и все сохранённые бронирования; чтение ничего не резервирует. Сервер
задаёт даты и время расчёта независимо от часов браузера. Возврат к дате обновляет
доступность, скрывая прежние интервалы на время загрузки.
Если сохранённая дата вышла за горизонт, календарь заново получает серверное сегодня
и границы; при сбое этот запрос можно повторить, просроченный выбор очищается.
Кнопка «Указать контакты» открывает третий шаг: имя, email и сводку с полным
интервалом. Возврат сохраняет контакты; смена типа или даты снимает прежний слот.
«Подтвердить бронирование» сохраняет запись, затем показывает «Встреча забронирована»
с нормализованными контактами. Письмо не отправляется: сохраните детали с экрана.
Подтверждение восстанавливается после обновления той же вкладки.
Адрес работает напрямую, после обновления и с обычной историей браузера.
Backend доступен на http://127.0.0.1:3000. Проверка состояния:

```bash
curl --fail --silent --show-error http://127.0.0.1:3000/health
# {"status":"ok"}
```

Ctrl+C останавливает обе части и освобождает порты. Ошибка запуска одной части завершает общий запуск.
Занятый выбранный порт вызывает ошибку; автоматического перехода на другой порт нет.

При ошибке сначала смотрите журнал backend: неверный/отсутствующий `DATABASE_PATH`,
права файла/каталога, повреждение или неподдерживаемая схема останавливают запуск
до HTTP. Проверьте тот же абсолютный путь и доступ к файлу и соседнему journal;
не удаляйте БД и не запускайте подготовку поверх неё. `db:prepare` отказывается
заменять существующий файл. При занятом порте остановите прежний процесс или явно
выберите другой порт. Если `/health` работает, но UI не получает данные, проверьте
`API_PROXY_TARGET` и `/api` proxy. Ошибка SQLite/ожидание блокировки при POST
оставляет неизвестный исход, поэтому повторяйте исходную попытку после устранения
причины.

Единственный исходник HTTP-контракта — [contract/main.tsp](contract/main.tsp),
настройки компилятора — [contract/tspconfig.yaml](contract/tspconfig.yaml).
TypeSpec 1.17.0 выпускает [OpenAPI 3.1](contract/openapi.json), затем
`@hey-api/openapi-ts` 0.99.0 — модели, схемы, SDK и типы ручных Fastify-обработчиков;
детерминированный адаптер дополняет их реестром операций и
[документацией API](contract/API.generated.md). `mise run api:generate` выполняет
всю цепочку. Генерируемые `contract/openapi.json`, `contract/API.generated.md` и
весь `contract/src/generated/` сохраняются в Git; вручную их не меняют.
`mise run api:check` офлайн компилирует TypeSpec и генерирует ожидаемые артефакты
во временный каталог: сравнивает байты и весь набор файлов, включая новые,
отсутствующие и лишние, без исправления сохранённых файлов. Сохраняются валидация
OpenAPI/JSON Schema и проверка фактических значений выпущенных схем.
Эта проверка и компиляция всех трёх частей входят в `mise run check` и существующий CI.
Ajv2020 проверяет запросы и ответы без автоматического изменения значений; клиент
проверяет также статус и тип содержимого. Backend не импортирует браузерный SDK.

Владелец открывает `/owner` напрямую или по ссылке «Владельцу календаря» в шапке.
По умолчанию открыты «Бронирования» за период «Предстоящие и текущие»; доступны
«Прошедшие», «Все» и вкладка «Типы встреч» с формой создания. Первый пустой запуск
предлагает создать тип; созданный тип сохраняется в SQLite и появляется у гостя.
Записи показывают тип/длительность, московскую дату и полный интервал, имя/email.
Предстоящая, текущая и завершившаяся встречи различаются по серверному времени
успешного чтения (`X-Server-Time`), а не по часам браузера. Состояние актуально на
момент загрузки; периодического опроса нет. У каждого списка независимы загрузка,
ошибка и повтор. «Обновить» сохраняет ввод и прежние строки; при сбое они помечены
устаревшими, время последней успешной загрузки не меняется. Переключение вкладок
сохраняет форму и незавершённую отправку. Типы нельзя изменять или удалять.
Операции не требуют входа.

Обе формы до POST сохраняют UUID и неизменяемые исходные данные в `sessionStorage`
вкладки; при недоступном хранилище запрос не отправляется. Во время отправки и при
неизвестном исходе поля и новая попытка заблокированы: запись могла сохраниться.
«Повторить создание» / «Повторить подтверждение» и обновление той же вкладки
используют прежние ключ/данные и получают сохранённый результат без дубля, даже
после окончания встречи. Закрытие вкладки или утрата её контекста не обещают
восстановления экрана; серверная запись сохраняется. Окончательный отказ позволяет
исправить данные и начать новую попытку. «Слот уже занят» удерживает фокус и
закрывается Escape; затем слот снят, контакты сохранены и доступность загружается
заново. Прошедшее время объясняется отдельно. Ошибка обновления даёт повтор,
прежние слоты недоступны.

Frontend использует относительный `/api`; Vite dev/preview проксирует его на
`http://127.0.0.1:3000`. Для другого backend задайте `API_PROXY_TARGET` при запуске
frontend. При отдельном размещении собранной статики настройте тот же `/api` на
reverse proxy.

Для backend можно задать `HOST` (по умолчанию `127.0.0.1`) и `PORT` (по умолчанию `3000`):

```bash
HOST=127.0.0.1 PORT=3100 mise run dev:backend
```

`PORT=0` выбирает свободный порт; фактический адрес выводится в журнал.
Для Vite порт можно задать через аргумент: `mise run dev:frontend -- --port 5174`.
`preview:frontend` предназначен для локального просмотра сборки.
Изменения зависимостей выполняются через `mise exec -- npm ...`; повторная установка — `mise run setup`.
HTTP smoke проверяет `/health`, HTML frontend и его JS-ресурс на собственных свободных loopback-портах.
Готовность ограничена 30 секундами, запрос — 5 секундами; при ошибке выводятся адрес и журналы процессов.
После успеха и ошибки серверы и соединения закрываются. Проверка не требует вручную запущенных серверов
и не проверяет отрисовку React в браузере.

Playwright выполняет сценарии обеих ролей через роли и доступные названия: главную,
прямое открытие/reload/историю `/booking` и `/owner`, создание типа → подтверждение
гостя → обновление владельца со сверкой сохранённой записи через API, ошибки,
восстановление попыток, независимые списки, клавиатуру и ширины 320/1440 px.
Он обслуживает готовую сборку через Vite preview на `http://127.0.0.1:4183`;
порт должен быть свободен, уже запущенный сервер не переиспользуется. Backend для этих
страниц запускается на `http://127.0.0.1:3183` с отдельной временной SQLite для каждого
сценария. Проверки доступности используют внедряемые серверные часы через отдельный
тестовый процесс и файл времени; production не имеет переменной для подмены часов
или служебных HTTP-маршрутов. Preview, backend и браузерные контексты завершаются после успеха и ошибки.
После запуска HTML-отчёт сохраняется в игнорируемом `playwright-report/`;
открыть его можно через `mise exec -- npx playwright show-report`.
При неуспехе trace и скриншот сохраняются в игнорируемом `test-results/`;
trace можно открыть через `mise exec -- npx playwright show-trace <путь-к-trace.zip>`.
В GitHub Actions отчёт и доступная диагностика публикуются в артефакте
`playwright-diagnostics-<run_id>-<run_attempt>` на 14 дней, в том числе после ошибки check.
Это проверка локальной сборки; публичный хостинг также должен отдавать frontend для `/booking` и `/owner`.

Каждый независимый набор Vitest получает отдельный временный каталог/файл SQLite;
при restart используется тот же файл. Playwright подготавливает пустую БД на тест,
а данные непустых/граничных сценариев принадлежат только проверочному окружению.
Потерю/искажение ответа можно вызвать на браузерной границе; серверные гарантии
дополнительно проверяются настоящим HTTP и сохранёнными данными. Контролируемые
остановки до/после commit синхронизированы маркером тестового процесса. Production
не имеет переключателей тестового времени/сбоев. Падение backend не доказывает
стойкость к аварии ОС или питания: действуют предпосылки исправного постоянного
диска и синхронизации по [ADR хранения](docs/adr/0003-booking-storage.md).

Матрица AC1–AC12/T1–T8 и пределы release-доказательств находятся в
[приёмке записи](docs/booking-acceptance.md); SHA, журналы, внешние снимки и итоговое
независимое ревью фиксируются в Answer задач графа.
Опубликованный v0.1.0 и локальное дополнение TypeSpec разграничены в
[приёмке шага 6](docs/step-6-readiness.md); CI базового выпуска не подтверждает новый SHA.

`check` возвращает ненулевой код при ошибке любого обязательного шага и не исправляет исходники или lockfiles.
Установленный Git-hook для `check` не нужен: в CI достаточно `mise install --locked`,
`mise exec -- npm ci`, `mise run browser:install -- --with-deps` и `mise run check`;
`setup` и `hooks:install` в CI не требуются. Этот порядок следует
[рекомендациям Playwright для CI](https://playwright.dev/docs/ci).

Общий лимит браузерного набора — 2 минуты локально и 5 минут в CI, где весь
набор выполняется одним worker одновременно с HTTP-проверками. Лимит отдельного
сценария остаётся 15 секунд, готовности preview — 30 секунд.

## Запуск в Docker

Из чистого checkout с установленным Docker соберите Linux-образ. Node.js 24.22.2,
зависимости по lockfile, проверка производных API и сборка приложения выполняются
внутри Docker; локальные Node, mise и файл БД для этого не нужны:

```bash
docker build -t call-calendar:local .
docker run --name call-calendar --rm -p 3817:3817 -e PORT=3817 call-calendar:local
```

Откройте http://127.0.0.1:3817. По тому же адресу доступны `/booking`, `/owner`,
`/api` и `/health`; прямое открытие и обновление клиентских страниц работают.
Один процесс Fastify раздаёт собранный интерфейс и API, отдельный Vite не запускается.
В контейнере `HOST=0.0.0.0`, порт по умолчанию — `3000`; при изменении `PORT`
укажите этот же внутренний порт справа в `-p`. `EXPOSE 3000` — описание порта
по умолчанию, оно само не публикует порт на компьютере.

Сборка явно подготавливает пустую SQLite с текущей схемой по пути
`/app/data/calendar.sqlite`. Контейнер запускается от пользователя `node`
(UID/GID `1000:1000`), которому доступны запись файла и соседнего journal.
Новый отдельный контейнер без постоянного хранилища начинает с пустыми списками
типов встреч и бронирований. `docker restart` того же контейнера сохраняет его
записываемый слой; удаление и создание нового контейнера сбрасывает эти данные.
Контекст сборки ограничен исходниками, manifests и контрактом через `.dockerignore`;
локальные зависимости, результаты сборки, БД, `.env` и сессии в него не включаются.

### Постоянное локальное хранилище Docker

Создайте отдельный Docker volume и **явно** подготовьте файл один раз. Параметр
`volume-nocopy` отключает неявное копирование пустой БД из образа в том:

```bash
docker volume create call-calendar-data
docker run --rm --user root \
  --mount type=volume,src=call-calendar-data,dst=/app/data,volume-nocopy \
  call-calendar:local chown node:node /app/data
docker run --rm \
  --mount type=volume,src=call-calendar-data,dst=/app/data,volume-nocopy \
  call-calendar:local node backend/dist/prepare.js
docker run --name call-calendar-persistent -p 3817:3817 -e PORT=3817 \
  --mount type=volume,src=call-calendar-data,dst=/app/data,volume-nocopy \
  call-calendar:local
```

При последующих запусках используйте последний `docker run` с тем же томом,
без повторной подготовки. Перезапуск, пересоздание контейнера и пересборка образа
не заменяют файл в подключённом томе. Применяются прежние гарантии SQLite при
исправном постоянном диске; удаление тома удаляет данные.

Вместо volume можно подключить отдельно подготовленный каталог на локальном диске
через `--mount type=bind,src=/абсолютный/путь,dst=/app/data`. Файл и каталог должны
быть доступны для чтения и записи UID/GID `1000:1000`; подключайте весь каталог,
чтобы SQLite мог создавать journal. Для другого расположения задайте абсолютный
`DATABASE_PATH` внутри контейнера и подключите содержащий его каталог.
Существующая команда `node backend/dist/prepare.js` создаёт файл по этому пути
и отказывается заменять существующий. Обычный запуск лишь открывает и проверяет
файл: отсутствующая, недоступная, повреждённая или неподдерживаемая БД останавливает
сервис. Новый пустой том с `volume-nocopy` без явной подготовки также не запустится.

## Локальные хуки

После `setup` каждый pre-commit вызывает общие `mise run lint` и `mise run format:check`
для всего рабочего дерева, включая незакоммиченные изменения. Нарушение блокирует коммит.
Хук только проверяет: не исправляет файлы, не добавляет их в индекс, не прячет изменения в stash
и не создаёт коммиты. Исправьте код или запустите `mise run format`, проверьте diff и добавьте
нужные изменения в индекс самостоятельно.

`mise run hooks:install` повторно подключает хук текущего клона; флаг `--mise` позволяет Git
найти закреплённые инструменты без активации mise в shell. Сам `mise` должен быть в `PATH`.
Проверить хук без коммита можно командой `mise exec -- hk run pre-commit`.
