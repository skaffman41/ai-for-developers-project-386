# Development workflow

Используй Matt Pocock Skills и существующий [локальный трекер](issue-tracker.md). Этот документ дополняет процедуры skills соглашениями репозитория и фиксирует явные уточнения пользователя.

## Приоритет и границы разрешения

Соблюдай системные ограничения безопасности и доступа. В их рамках порядок такой: явные актуальные инструкции пользователя → существующие требования проекта → процедуры установленных skills → дополнительные соглашения workflow. Оригинальные установленные skills не редактируй.

Команда `$implement <id>` разрешает реализацию только указанного тикета по согласованной спецификации, необходимые локальные проверки и отдельный коммит результата. Описанная в тикете подготовка согласованного toolchain и зависимостей входит в его объём; установка дополнительных инструментов вне этого объёма требует разрешения. Ограничения текущего запроса, например «без коммита» или «только исследование», имеют приоритет. Push и переход к следующей задаче требуют отдельных явных запросов.

Статус `ready-for-agent` означает готовность текста задачи к запуску, а не разрешение реализовать всю очередь. Старые ограничения отдельного запроса в Comments — история: применяй последующее явное разрешение, сохраняя постоянные ограничения проекта. Для шага, уже разрешённого тикетом и текущим запросом, повторное подтверждение не требуется.

## План до реализации

После согласования спецификации, границ тестирования и декомпозиции сохрани спецификацию и отдельные тикеты с блокирующими связями в трекере. Проверь их ссылки и зафиксируй план отдельным Conventional Commit до начала реализации, например `docs: add app skeleton specification and tickets`.

Если части плана или промежуточный результат уже закоммичены, сохрани историю и добавь только недостающее. Не выполняй reset, rebase, amend или force push ради изменения порядка либо названий коммитов. Если безопасно разделить работу без потерь не удаётся, опиши конкретное пересечение и запроси решение.

## Один тикет — один цикл

1. Проверь ветку, `git status --short`, последние коммиты, рабочий и staged diff, включая untracked-файлы. Определи назначение уже существующих изменений по истории и контексту. Сохрани их; при неясном пересечении с задачей уточни только это пересечение. Не очищай рабочее дерево и не включай чужую работу в коммит.
2. Разреши идентификатор по правилам трекера. Прочитай спецификацию и тикет целиком, проверь зависимости и наличие согласованного плана в Git. При отсутствующем плане сначала зафиксируй его; при незавершённой зависимости реализацию не начинай. Уже выполненную задачу не реализуй заново без запроса на пересмотр.
3. Установи `claimed` перед реализацией. Выполни один проверяемый результат тикета, используя подходящие skills. Технические ошибки обрабатывай по [tool-recovery.md](tool-recovery.md), сохраняя критерии приёмки.
4. Выполни предусмотренные тикетом проверки и Testing Decisions спецификации. Проверяй типы и затронутые тесты по мере работы; полный существующий suite запусти перед завершением. TDD используй там, где задача предусматривает новые тесты на уже согласованной границе; подтверждённую границу повторно согласовывать не нужно. Если применимой команды ещё нет или требование не относится к этой задаче, явно объясни это в Answer. Непройденная обязательная проверка оставляет задачу незавершённой.
5. Оцени необходимость независимого `code-review` до коммита по содержанию и риску изменений: он нужен для существенного изменения поведения, контрактов, архитектуры или нетривиальной логики. Число изменённых строк само по себе не определяет значимость. Для небольших правок документации, форматирования и простых локальных изменений достаточно предусмотренных проверок и самопроверки diff; у документации проверь ссылки, пути и `git diff --check`. Если проводишь ревью, исправь выявленные дефекты и повтори затронутые проверки. Явный запрос пользователя на ревью имеет приоритет.
6. Закрой задачу по правилам трекера: в Answer сохрани результат, проверку каждого критерия, команды и существенные ограничения; только после выполнения всех критериев установи `resolved`. Критерии всей спецификации отмечай лишь при наличии требуемых доказательств, не по одному факту завершения дочернего тикета.
7. Проверь staged diff и создай отдельный Conventional Commit завершённой задачи: `type(scope): description`, scope необязателен. Добавляй конкретные относящиеся к ней файлы или hunks, не используй общий `git add .` при посторонних изменениях. Измени lockfile только предусмотренной командой установки, не вручную для сокрытия конфликта.
8. Проверь итоговый `git status` и коммит. Сообщи SHA, результат проверок и оставшиеся блокировки; перечисли намеренно оставленные чужие изменения. На этом цикл заканчивается.

При реальной блокировке сохрани достигнутый результат и невыполненные критерии в Answer или Comments. Выбери незавершённый статус по [triage-labels.md](triage-labels.md); `needs-info` не закрывает зависимость. Не создавай коммит с заявлением о завершении; необходимый промежуточный коммит явно обозначай как незавершённый и учитывай ограничения пользователя.

## Согласование со skills

- `setup-matt-pocock-skills` уже настроил локальный трекер, роли и single-context. Обычный запуск `$implement` не требует повторной настройки или выбора трекера.
- `implement` связывает реализацию, применимый TDD, проверки и коммит. По явному решению пользователя требование исходного skill вызывать `code-review` после каждой задачи заменено условием пункта 5: при `$implement` ревью выполняется только для существенных изменений, когда оно полезно, либо по отдельному запросу пользователя. Это локальное уточнение workflow; оригинальный skill остаётся без изменений. Спецификация определяет согласованные границы тестов; инструкции текущего запроса могут ограничить коммит или объём работы.
- Для ревью до коммита опорная точка по умолчанию — HEAD перед началом задачи; явно заданная пользователем точка важнее. В `code-review` передай её SHA, критерии тикета и фактический diff. Рабочие изменения смотри через `git diff <base> -- <files>`, staged — `git diff --cached <base> -- <files>`, новые файлы — отдельно, например `git diff --no-index /dev/null <file>`. Код 1 последней команды означает наличие различий. Сохрани обе независимые оси ревью: Standards и Spec. После коммита применим обычный `git diff <base>...HEAD`. Не создавай предварительный коммит только ради формы diff.
- Ограничение конкретного инструмента из skill соблюдай для его маршрута. Оно не отменяет независимые безопасные действия через другие разрешённые инструменты; пример с браузером и npm описан в tool-recovery. При настоящем неразрешимом конфликте назови правило и источник, предложи минимальную адаптацию, не редактируя skill.
