# Development workflow

Используй глобальные Matt Pocock Skills и [GitHub Issues](issue-tracker.md). Этот документ задаёт проектные границы их процедур; оригинальные установленные skills сохраняются. Подготовка окружения — [skills.md](skills.md).

## Приоритет и команды

Соблюдай системные ограничения доступа; в их рамках актуальные явные инструкции пользователя имеют приоритет над соглашениями проекта и процедурами skills. Старые ограничения отдельного запроса в импортированных Comments — история. Уже разрешённый шаг повторного подтверждения не требует.

Ручные команды вызываются как `$<name>`. Если host не предоставляет Skill tool или ручную команду, прочитай целиком `~/.agents/skills/<name>/SKILL.md` и выполни процедуру вместе с её необходимыми ссылками. Для `grill-with-docs` прочитай также `grilling` и `domain-modeling`. Оригинальные файлы не изменяй.

| Команда                  | Результат и полномочия                                                                                                                |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| `$grill-with-docs`       | Уточнение замысла и запись принятых терминов/решений в `GLOSSARY.md` и `docs/adr/` по мере необходимости                              |
| `$to-spec`               | Синтез обсуждения в спецификацию GitHub, согласование ещё не определённых Testing Decisions                                           |
| `$to-tickets <spec>`     | Согласование графа проверяемых результатов и публикация native sub-issues с блокерами                                                 |
| `$implement <issue>`     | Один цикл одного согласованного тикета в рабочей ветке, назначения, отчёты, проверки и отдельный локальный коммит                     |
| `$implement-spec <spec>` | Весь согласованный граф в интеграционной ветке, свежий контекст исполнителя для каждой задачи, отдельные worktree и локальные коммиты |

Оба режима реализации разрешают назначать выбранные Issues и публиковать отчёты. Подготовка toolchain и зависимостей, прямо предусмотренная тикетом, входит в его объём. Дополнительные инструменты вне согласованного объёма требуют решения пользователя. Push, создание PR и merge в `main` выполняются только по отдельным явным командам. `$implement` заканчивается после одной задачи; `$implement-spec` продолжает согласованный граф без запроса на каждый следующий тикет. Ограничения текущего запроса («без коммита», «только исследование») сохраняют приоритет.

## План до реализации

После согласования спецификации, Testing Decisions и графа опубликуй спецификацию и задачи в GitHub. Проверь полные тексты, native parent и блокеры, затем сохрани снимок `docs/plans/<feature-slug>/vN/` отдельным Conventional Commit **до изменения реализации**:

- `spec.md` и отдельный Markdown-файл каждой задачи: согласованные тексты, критерии и Testing Decisions;
- `manifest.json`: репозиторий, версия, факт согласования, исходный commit, номера/URL Issues, соответствие файлов, SHA-256 байтов снимков и опубликованных тел, номера блокеров;
- ссылки на согласованную версию в отчёте GitHub.

Этот снимок — базовая линия реализации, а GitHub — канонический трекер. Сверь тела с хешами manifest и прочитай последующие комментарии. Отмечай прогресс комментариями, назначениями, состояниями и метками; эти изменения не переписывают старый снимок. Если меняются согласованные требования, критерии, Testing Decisions или граф, согласуй изменившийся объём, создай `vN+1` с полными актуальными текстами и новым manifest, обнови GitHub и зафиксируй новую версию отдельным planning-коммитом до её реализации. Прежние версии остаются неизменными. Техническое уточнение отчёта без изменения объёма не требует новой версии или повторного разрешения.

Сохраняй существующую историю. Добавляй недостающую часть плана новым коммитом; reset, rebase, amend и force push ради порядка коммитов не применяются. При реальном пересечении согласованного плана с чужой работой уточни конкретное пересечение.

## Один тикет — один цикл

1. Проверь ветку, `git status --short`, последние коммиты, рабочий и staged diff, untracked-файлы. Определи назначение существующих изменений; сохрани их. Создай рабочую ветку от подтверждённой базы или используй явно выделенную для задачи. При неясном пересечении уточни только его; чужую работу в коммит не включай.
2. Разреши Issue по [issue-tracker.md](issue-tracker.md), назови заголовок, прочитай тело, все комментарии, родительскую спецификацию и каждый блокер. Проверь planning-коммит, соответствие снимка и готовность зависимостей по разделу ниже. При отсутствующем плане сначала зафиксируй согласованный план; при невыполненной зависимости реализацию не начинай. Выполненную задачу повторно реализуй только по запросу на пересмотр.
3. Назначь исполнителя и опубликуй начало работы с веткой. Выполни результат тикета подходящими skills. Следуй Testing Decisions и актуальным инструкциям пользователя: TDD применяй на согласованной границе при явно порученных новых тестах; вызов режима реализации сам по себе не поручает их добавление. Ошибки обрабатывай по [tool-recovery.md](tool-recovery.md).
4. Выполни критерии и предусмотренные проверки. По мере работы проверяй типы и затронутые существующие тесты; перед завершением запусти полный существующий `mise run check`. Если проверка неприменима, объясни причину в отчёте. Непройденная обязательная проверка оставляет результат незавершённым.
5. До коммита оцени содержательность независимого `code-review`: он нужен при существенном изменении поведения, контрактов, архитектуры или нетривиальной логики, а также по явному запросу. Число строк само по себе не критерий. Сохрани обе независимые оси Standards и Spec; исправь дефекты и повтори затронутые проверки. Для простых правок достаточно самопроверки; у документации проверь ссылки, пути и `git diff --check`.
6. Проверь staged diff и создай отдельный Conventional Commit: `type(scope): description`, scope необязателен. Добавляй конкретные файлы или hunks задачи, сохраняя посторонние изменения. Lockfile меняй штатной командой, предусмотренной планом.
7. Опубликуй `Answer`/отчёт в Issue: результат каждого критерия, SHA, ветка, команды и итоги проверок, ревью, существенные ограничения. Для реализации явно укажи, готов ли результат локально или уже интегрирован. Оставь Issue открытым до merge по правилам ниже.
8. Проверь итоговые статус и коммит. Сообщи SHA, проверки, блокировки и намеренно оставленные чужие изменения. Для `$implement` цикл завершён; следующая задача требует нового запроса. Для `$implement-spec` передай результат координатору графа.

Для ревью до коммита опорная точка — HEAD перед задачей, если пользователь не задал другую. Передай SHA, критерии и фактический diff: `git diff <base> -- <files>`, staged diff и отдельное содержимое новых файлов. `git diff --no-index /dev/null <file>` возвращает 1 при наличии различий; это не ошибка проверки. После коммита применим `git diff <base>...HEAD`. Предварительный коммит ради формы diff не нужен.

## Готовность и завершение

**Implementation-ready** — критерии результата выполнены, обязательные проверки и необходимое ревью успешны, есть локальный коммит и отчёт. Issue реализации ещё открыт. **Integrated** — связанный PR успешно merged в `main`, нужный коммит присутствует в `main`, критерии подтверждены; теперь Issue закрывается с причиной `completed`. Сам факт `closed` или метка `ready-for-agent` этого не доказывает.

Блокер реализации выполнен для следующего тикета в одном из двух случаев:

- **В том же явно запущенном графе `$implement-spec`:** отчёт указывает успешные критерии и проверки; SHA результата включён в текущую интеграционную ветку (`git merge-base --is-ancestor <sha> <integration-branch>`); после включения сохраняются необходимые проверки. Открытый Issue с таким доказательством разблокирует только эту ветку и этот запуск.
- **Вне этого запуска/ветки:** подтверждены merge связанного PR в `main`, наличие результата в `main` и выполнение критериев. Одного локального отчёта из другого запуска недостаточно.

Для задачи исследования или решения достаточно принятого `Answer` с доказательствами и закрытия `completed` по правилам трекера; PR с кодом не обязателен. Отклонённый (`wontfix`/`not_planned`), неудачный или отменённый результат никогда не выполняет зависимость. Пересмотри зависимый объём или дождись успешного результата.

При реальной блокировке сохрани достигнутое и невыполненные критерии в комментарии/Answer, примени незавершённую роль triage. Промежуточный коммит обозначай как незавершённый; не заявляй приёмку. Критерии спецификации подтверждай собственными доказательствами, а не одним завершённым ребёнком.

## Весь согласованный граф

`$implement-spec` использует граф native блокеров и согласованный снимок. Координатор создаёт интеграционную ветку, выбирает доступный frontier и поручает каждую задачу исполнителю со свежим контекстом, указав спецификацию, Issue, снимок, базовый SHA, полномочия и владельца файлов. Независимые доступные задачи могут выполняться параллельно в отдельных worktree.

Каждый исполнитель проверяет происхождение своей ветки и чистоту своего worktree до начала. При несовпадении базы используй безопасное объединение либо новый выделенный worktree; сохраняй чужие изменения. Исполнитель включает актуальную интеграционную ветку в свою перед сдачей. Координатор через отдельного merger включает готовый результат в интеграционную ветку, проверяет ancestry, отчёт и проверки, затем обновляет frontier. Каждая задача сохраняет отдельный Conventional Commit.

Перед подробным отчётом исполнитель отправляет короткое сообщение о готовности: Issue,
ветка, SHA коммита и его дерева (`git rev-parse HEAD^{tree}`), чистота worktree, результаты
обязательных проверок и двух осей ревью, указатель на доказательства и ограничения.
Merger начинается после этого сообщения; наличие коммита без подтверждённой готовности
не завершает задачу. Координатор ожидает события агентов, читает новый diff при изменении
SHA и передаёт контекст указателями. Для больших журналов и JSON сначала отбирай нужные
поля или строки, затем возвращай результат в контекст.

Промежуточный merger может использовать успешную проверку исполнителя при чистом
fast-forward, если дерево совпадает с проверенным результатом, toolchain и зависимости
совпадают, а критерии и команды проверок не менялись. Он всё равно подтверждает ancestry,
чистоту и защищённые файлы и ссылается на исходный отчёт. Разрешение конфликтов, новые
изменения или другое окружение требуют применимых повторных проверок. Полный check каждой
задачи до коммита и финальный check всего интеграционного графа остаются обязательными.

Проектные полномочия уточняют upstream `implement-spec`: автоматическое создание draft PR, пометка ready и закрытие Issues реализации заменяются локальными коммитами и отчётами до отдельной команды публикации. Разрешено объединять собственные ветки задач в локальную интеграционную ветку; merge в `main` требует отдельной команды. После всего графа оцени итоговое существенное изменение через независимое ревью и выполни итоговые проверки. На этом остановись с отчётом о готовности, SHA и открытых Issues.

Для визуальных изменений до публикации сохраняй скриншоты и измерения вне репозитория.
При подготовке PR приложи выбранные снимки или ссылку на доступные артефакты; локальный
путь служит дополнением. Отчёт Playwright из CI публикуется как Actions artifact;
падения дополнительно сохраняют trace и скриншот. Это диагностические материалы,
а не система эталонных скриншотов.

Cleanup касается только созданных этим запуском чистых worktree и веток, чьи результаты сохранены; проверь статус и принадлежность перед удалением. Рабочую интеграционную ветку с результатом сохрани. Безопасное сохранение чужих изменений имеет приоритет над upstream reset/cleanup.
