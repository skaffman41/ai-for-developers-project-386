# Issue tracker: GitHub Issues

Канонический трекер карт решений, спецификаций и задач — [skaffman41/ai-for-developers-project-386](https://github.com/skaffman41/ai-for-developers-project-386/issues). `.scratch/` сохраняется как неизменяемый архив этапа 2; новые записи туда не добавляются. Сопоставление старых путей и ID, источники и доказательства импорта — [tracker-migration.md](tracker-migration.md).

## Resolve a reference

1. Номер `3` или `#3` означает Issue целевого репозитория. URL должен явно указывать на `github.com/skaffman41/ai-for-developers-project-386/issues/<number>`. Для другого репозитория сначала установи намерение пользователя; не подменяй его текущим `origin`.
2. Старый ID `02-run-application` или путь `.scratch/app-skeleton/issues/02-run-application.md` разрешай только по таблице миграции. Один `02` не является старым глобальным ID и не означает новый тикет `02-…`; для GitHub используй обычный номер `2` или `#2`.
3. Прочитай полное тело и все комментарии Issue, его родительскую спецификацию/карту и каждый блокер, включая их результаты. Через API используй пагинацию для комментариев, дочерних задач и зависимостей. Сверь native parent/sub-issues и `blocked_by` с текстовыми ссылками; расхождение сначала разреши по согласованному плану.
4. Перед реализацией назови заголовок выбранного тикета. Не создавай замену отсутствующей задаче и не выбирай похожий ID. Готовность зависимостей проверяй по [development-workflow.md](development-workflow.md#готовность-и-завершение).

## Access and operations

Используй закреплённый gh через mise. Перед первой записью проверь `full_name` и права по [skills.md](skills.md#github-cli). Каждую команду адресуй явно:

```sh
mise exec -- gh issue view 3 -R skaffman41/ai-for-developers-project-386 --comments
mise exec -- gh issue list -R skaffman41/ai-for-developers-project-386 --state all
mise exec -- gh api --paginate 'repos/skaffman41/ai-for-developers-project-386/issues/3/comments?per_page=100'
mise exec -- gh api --paginate 'repos/skaffman41/ai-for-developers-project-386/issues/3/dependencies/blocked_by?per_page=100'
```

`gh issue view` показывает тело; для полного чтения комментариев API с пагинацией является проверяемым маршрутом. `gh issue list` — обзор: для полного инвентаря используй API `issues?state=all&per_page=100` с `--paginate` и отделяй pull requests от Issues. `gh api` всегда использует полный путь `repos/skaffman41/ai-for-developers-project-386/...`, без неявных `{owner}`/`{repo}`. Передавай тела через структурированный JSON (`--input`) или `--body-file`, сохраняя переносы строк.

| Операция skill         | Действие в GitHub                                                                                                                      |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Publish / fetch / list | Создай отдельный Issue; читай полное тело и комментарии; фильтруй список по типу, triage и состоянию                                   |
| Parent / child         | Ссылка на родителя в теле и native sub-issue; POST `issues/<parent>/sub_issues` с `sub_issue_id`, равным числовому database ID ребёнка |
| Blocking               | Native POST `issues/<child>/dependencies/blocked_by` с `issue_id` блокера; в тексте оставь проверяемые ссылки или `None`               |
| Triage                 | Примени одну роль и одну категорию по [triage-labels.md](triage-labels.md)                                                             |
| Claim                  | Назначь исполнителя и опубликуй начало работы с веткой; это не новая роль triage                                                       |
| Comment / Answer       | Добавляй комментарии, сохраняя историю; в итоговом `Answer` укажи критерии, SHA, проверки и ограничения                                |
| Close / reject         | Используй правила завершения ниже; причина закрытия хранится отдельно от меток                                                         |

Для проверок связей доступны GET `issues/<parent>/sub_issues`, `issues/<child>/parent` и `issues/<child>/dependencies/blocked_by`. Перед записью считай существующие связи; повторная операция не должна добавлять дубль. После записи перечитай результат API. Публикация задач, назначения и отчётов входит в полномочия явно вызванной команды; публикация кода регулируется отдельно workflow.

## Specifications and implementation tickets

Одна спецификация — отдельный Issue с `type:spec`; задачи реализации — её native sub-issues с `type:task`. Полный текст содержит результат для пользователя, критерии приёмки, Testing Decisions, ссылку на родителя и блокирующие связи. Номер выдаёт GitHub; локальная нумерация `NN` больше не используется.

После согласования сохрани неизменяемый снимок плана в Git по [development-workflow.md](development-workflow.md#план-до-реализации). GitHub остаётся местом статусов, обсуждений и отчётов. Тело должно соответствовать согласованной версии; изменение требований фиксируется новой версией снимка, а прогресс — комментариями.

Завершение реализации, причины закрытия и готовность блокеров проверяй по разделу [«Готовность и завершение»](development-workflow.md#готовность-и-завершение). При операции Close передавай соответствующий `state_reason` GitHub, а результат и доказательства сохраняй в отчёте Issue.

Исторические Issues этапа 2 закрыты как `completed`: их работа уже присутствует в исходном коммите архива, что подтверждает таблица миграции.

## Wayfinding operations

- **Map:** отдельный Issue с `type:map` и разделами Notes, Decisions so far, Not yet specified по шаблону `wayfinder`.
- **Child:** native sub-issue карты; тип — ровно одна метка `type:research`, `type:prototype`, `type:grilling` либо `type:task`. Роли triage не назначаются задачам решений (`research`, `prototype`, `grilling`) и карте. `task` использует обычные правила реализации и triage.
- **Frontier:** открытые задачи, у которых выполнены все native блокеры; при нескольких доступных задачах используй порядок согласованного графа. `not_planned`, `wontfix`, неудачный или отменённый результат блокер не выполняет.
- **Claim:** назначь исполнителя и добавь комментарий о начале работы. Текущее выполнение определяется назначением и отчётом, а не меткой `claimed`.
- **Resolve a decision:** опубликуй полный `Answer` с доказательствами; после принятия результата пользователем или в пределах явно делегированного решения закрой как `completed`. Добавь вывод и ссылку в Decisions so far карты. Для исследования или решения PR с кодом не требуется; принятое решение может разблокировать зависимую задачу.

Карта и родительская спецификация закрываются только после выполнения собственных критериев и всех необходимых дочерних результатов. Завершение одного ребёнка не доказывает приёмку родителя.
