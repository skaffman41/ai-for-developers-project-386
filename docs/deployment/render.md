# Ручная выкладка на Render Free через MCP (история)

С 2026-11-11 активный маршрут — [Railway](railway.md), выбранный пользователем
в [плане v2](../plans/step-7-render-free/v2/spec.md). При проверке Render доступ к
выбору исходников потребовал карту; ресурсы не создавались. Этот документ и
`render.yaml` сохранены как история v1 и не применяются для текущей выкладки.

Конфигурация подготовлена для [спецификации #55](https://github.com/skaffman41/ai-for-developers-project-386/issues/55).
Создание Blueprint, сервиса и деплой выполняются по отдельной явной команде после
merge нужной версии в `main`. Наличие файлов в Git ничего не публикует.
Текущий результат внешней проверки находится [ниже](#состояние-проверки).

## Подключение Codex

Используется официальный hosted endpoint `https://mcp.render.com/mcp` и вход через
браузер по [инструкции Render для Codex](https://render.com/docs/mcp-server#codex-desktop-and-cli-setup).
В отдельном доверенном checkout создайте `.codex/config.toml` из
следующего исторического шаблона (текущий `.codex/config.toml.example` относится
к Railway). Если файл уже существует, сохраните остальные настройки:

```toml
[mcp_servers.render]
url = "https://mcp.render.com/mcp"
enabled_tools = [
  "list_workspaces", "get_selected_workspace", "list_services", "get_service",
  "list_deploys", "get_deploy", "get_blueprint",
]

[mcp_servers.render.oauth]
client_id = "codex"
```

Затем из корня проекта:

```sh
codex mcp login render
codex mcp list
```

Завершите вход в Render и разрешение доступа в открывшемся браузере. OAuth
сохраняется в пользовательском хранилище Codex. Не задавайте `CODEX_HOME` внутри
checkout, не копируйте credential-файлы и не вставляйте токены в конфигурацию,
командную строку или отчёт. `.codex/config.toml` игнорируется Git.

Шаблон включает только чтение; он не ограничивает права самого аккаунта Render.
Порядок проверки полного каталога с временным снятием фильтра описан ниже:
отсутствие инструмента в allow list Codex не означает его отсутствия на сервере.
`/mcp` в Codex показывает подключение. Основание —
[официальная документация OpenAI о MCP](https://developers.openai.com/codex/mcp/).

Вместо прямого подключения можно установить официальный Render plugin и пройти
его браузерный OAuth. Используйте одно подключение, чтобы не перепутать аккаунты.
Для CI допустим документированный API key: в пользовательской секции Render
замените OAuth на `bearer_token_env_var = "RENDER_API_KEY"` и предоставьте значение
через окружение процесса из своего хранилища секретов. Это имя переменной, а не
место для ключа. Ручное подключение из шаблона не требует ключа.

## Проверка до создания ресурсов

После OAuth проверьте каталог отдельно от выполнения операций. Для прямого
подключения из шаблона:

1. Сохраните исходное значение `enabled_tools` секции `[mcp_servers.render]` в
   пользовательской заметке вне Git. В локальном `.codex/config.toml` временно
   удалите весь ключ `enabled_tools = [...]`, включая многострочный список и
   закрывающую `]`. Остальные настройки и OAuth оставьте на месте.
2. Перезапустите Codex и откройте `/mcp`. Без allow list клиент получает полный
   каталог Render. Попросите агента прочитать переданные сервером описания и схемы
   из протокольного `tools/list`, сохранив названия, обязательные параметры и enum
   из таблицы ниже. Это чтение каталога, без `tools/call` к `create_*`, `update_*`,
   `plan_blueprint`, `approve_blueprint`, `trigger_deploy` или другим операциям
   записи. Наличие инструмента в каталоге не разрешает его выполнение; команда на
   деплой для этого чтения не требуется.
3. Верните исходный `enabled_tools` в ту же локальную секцию. При неизменённом
   шаблоне скопируйте список из блока выше. Перезапустите Codex;
   `codex mcp get render --json` должен показать восстановленный список в
   `enabled_tools`. Через `/mcp` убедитесь, что снова доступны только разрешённые
   операции чтения. Если полный каталог получить не удалось, восстановите фильтр
   тем же способом и запишите ограничение, не делая вывод об отсутствии alpha-tools.

Теперь попросите агента выполнить только `list_workspaces`.
Выберите нужный workspace; сохраните его ID в локальном отчёте. Если их несколько,
агенту нужен явный выбор пользователя. Далее выполните `list_services` с этим
`workspaceId` и `includePreviews: false`. Запишите время, успешный ответ и названия
инструментов, исключив секреты и посторонние данные. Пустой список — допустимый
успех чтения. Подключение без успешного вызова этого не доказывает.

Сверьте **фактические** схемы инструментов с необходимыми возможностями:

| Назначение                     | Необходимые инструменты и параметры                                                                                                          |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Чтение                         | `list_workspaces`; `list_services(workspaceId, includePreviews)`; `get_service(serviceId, workspaceId)`                                      |
| План первой публикации         | `create_blueprint(repoUrl, branch, path, autoSync, workspaceId)`                                                                             |
| Контроль Blueprint             | `get_blueprint(blueprintId, workspaceId)`; `update_blueprint(blueprintId, autoSync, workspaceId)`                                            |
| Ручное применение конфигурации | `plan_blueprint(blueprintId, workspaceId)`; `approve_blueprint(blueprintId, workspaceId)`                                                    |
| Обновление кода и контроль     | `trigger_deploy(serviceId, clearCache, workspaceId)`; `list_deploys(serviceId, workspaceId)`; `get_deploy(serviceId, deployId, workspaceId)` |

Это ожидаемые контракты из
[официального исходника MCP](https://github.com/render-oss/render-mcp-server/tree/db8e54d13e462d7379f568e9129e25f9953f20b1),
а не инвентарь текущего подключения. Blueprint-инструменты находятся в public alpha.
Обычный `create_web_service` нельзя использовать как бесплатный обход: в проверенной
документации его `plan` перечисляет только платные варианты.
[Справка инструментов](https://github.com/render-oss/render-mcp-server#tools).

Если фактический каталог не даёт создать и вручную применить Blueprint с бесплатным
сервисом, остановитесь до создания. Сохраните отсутствующую возможность и оставьте
#57/#58 незавершёнными; платный тариф, Dashboard или REST не заменяют MCP-критерий.

## Доступ Render к исходникам

В [render.yaml](../../render.yaml) явно заданы публичный репозиторий
`skaffman41/ai-for-developers-project-386` и ветка `main`. Успех `gh`, браузерный
просмотр GitHub и авторизация MCP — отдельные факты: они не подтверждают, что
конкретный аккаунт Render может получить нужную ветку и файл Blueprint.

До создания сервиса проверьте этот репозиторий в списке доступных исходников Render
в форме New → Blueprint; не подтверждайте создание. Если нужен Git provider,
в Account Settings → Account Security → Git Deployment Credentials выберите
Add credential → GitHub и завершите браузерный flow, разрешив доступ только к
нужному репозиторию. Запишите результат проверки списка отдельно от MCP-read.
[Инструкция подключения Git provider](https://render.com/docs/git-provider).

Для публичного URL подключение Git provider может не требоваться. Всё равно нужна
Render-side проверка доступа; после разрешённого создания её дополняет успешный
план именно удалённого `main` и `render.yaml`. Пока изменения только локальные,
удалённый `main` не содержит подготовленную версию. Нельзя проверять её под видом
уже опубликованной или создавать ресурс из другой ветки.

## Подготовленная конфигурация и первая публикация

[render.yaml](../../render.yaml) задаёт один Docker web service: `plan: free`, один
экземпляр, `autoDeployTrigger: "off"`, без `disk`, внешней БД и preview environments.
Сборка использует корневой Dockerfile; запуск — его команду и подготовленную в образе
SQLite. Render выдаёт `PORT`, приложение слушает `0.0.0.0`; не фиксируйте `PORT` в
конфигурации. Проверка здоровья — `/health`.
[Справочник Blueprint YAML](https://render.com/docs/blueprint-spec),
[порт web service](https://render.com/docs/web-services#port-binding).

`autoSync` относится к самому Blueprint и **не задаётся** в YAML. После отдельного
разрешения на первую публикацию, успешных локальных проверок и merge/push в `main`:

1. Сверьте удалённый SHA `main`, содержимое Dockerfile и YAML с проверенной версией.
   Убедитесь в доступности alpha-инструментов и нужного workspace.
2. Временно разрешите в локальном MCP-фильтре только необходимые операции из таблицы.
   Через `create_blueprint` передайте `repoUrl` из YAML, `branch: "main"`,
   `path: "render.yaml"`, `autoSync: false`, выбранный `workspaceId` и имя Blueprint.
   Это уже создание объекта Blueprint: в подготовку #57 этот вызов не входит.
3. Сохраните ID и план первой синхронизации. Через `get_blueprint` проверьте
   `autoSync: false`, ветку и путь. План должен создавать только один Free Docker
   web service без дисков, БД, платных ресурсов и изменений чужих сервисов.
   При другом результате не одобряйте план.
4. Покажите конкретный план пользователю и примените его через `approve_blueprint`
   в пределах уже полученной команды на эту выкладку. Повторное разрешение нужно,
   только если план меняет согласованный объём или ресурсы. Не передавайте секреты через
   `manualEnvVars`: этой конфигурации они не нужны. Ошибочный или пустой план
   применять нельзя.
5. Сохраните ID сервиса/деплоя. Через `get_blueprint`, `get_service`, `get_deploy`
   дождитесь результата и проверьте Docker, Free, один экземпляр, отсутствие диска,
   `autoDeploy` выключен и `autoSync: false`. Ответ approve ещё не доказывает
   работоспособность приложения. Выполните публичную приёмку из #58.

Blueprint может иметь статус `paused` при отключённом auto-sync после первого
применения; это не статус здоровья сервиса. Значения и правила первого применения
описаны в [исходнике Blueprint tools](https://github.com/render-oss/render-mcp-server/blob/db8e54d13e462d7379f568e9129e25f9953f20b1/pkg/blueprint/tools.go).

## Последующие ручные обновления

После отдельной команды выкладки и merge/push проверенной версии в `main` сначала
прочитайте сервис и Blueprint: Free, Docker, `main`, автодеплой и auto-sync выключены.
При изменении только кода вызовите MCP `trigger_deploy` с подтверждёнными `serviceId`,
`workspaceId`, `clearCache: false`. Проверьте результат через `get_deploy`, включая
соответствие commit SHA выбранному удалённому `main`, затем `/health` и сценарии.
Если ветка продвинулась и SHA иной, не объявляйте ожидаемую версию опубликованной.

При изменении YAML выполните `plan_blueprint`, покажите изменения и
примените через `approve_blueprint` в пределах команды на эту выкладку;
при изменении согласованного объёма сначала уточните его. `autoSync: false`
сохраняется; при необходимости его явно выставляет `update_blueprint` до применения.
Отсутствие автодеплоя сервиса само по себе не отключает применение Blueprint:
это два независимых переключателя.
[Автодеплой сервиса](https://render.com/docs/deploys#configuring-auto-deploys),
[автоматическая синхронизация Blueprint](https://render.com/docs/infrastructure-as-code#disabling-auto-sync).

Сохраните время UTC, исходный SHA, версию/хеш конфигурации, параметры без секретов,
ID Blueprint/сервиса/деплоя, итог операции, публичный URL и результаты HTTP/браузерной
приёмки. Верните фильтр MCP к чтению. Push сам по себе не должен вызывать выкладку.

## Ограничения бесплатного стенда

Стенд учебный: раздел владельца календаря открыт без входа; используйте вымышленные
имена/email. Render Free засыпает после 15 минут без запросов, пробуждение занимает
около минуты. Изменения SQLite теряются при сне, перезапуске и новом деплое, включая
типы встреч, бронирования и результаты попыток. Атомарность и повторы действуют в
пределах текущей БД. Постоянный диск и внешняя БД не создаются. Сохранность локального
постоянного хранилища описана в README и [ADR 0003](../adr/0003-booking-storage.md).
[Ограничения Render Free](https://render.com/docs/free).
