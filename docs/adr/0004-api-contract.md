# Единый OpenAPI-контракт и повторяемые отправки

Для основной записи на встречу отдельное описание OpenAPI 3.1 является единственным источником HTTP-контракта. Из него получаем документацию, типизированный клиент, серверные типы и схемы проверки; обработчики и бизнес-логика пишутся вручную. При пяти операциях прямое описание требует меньше шагов, чем TypeSpec с выпуском того же OpenAPI. Независимые клиентские и серверные определения запрещены; производные файлы хранятся в Git, не редактируются вручную и проверяются повторной генерацией и компиляцией. Источник решения — [обсуждение API](https://github.com/skaffman41/ai-for-developers-project-386/issues/32), фактические возможности инструментов проверяются в [исследовании цепочки](https://github.com/skaffman41/ai-for-developers-project-386/issues/36).

Запросы проверяются без автоматического приведения типов, подстановки значений и удаления неизвестных полей. Согласованная нормализация текстов выполняется явно; ограничения длины применяются после удаления краевых пробелов. Сервер проверяет исходящие ответы до сериализации, клиент проверяет полученные ответы. Типизация и сериализация не заменяют runtime-проверку; непонятный ответ операции создания не означает ни успеха, ни окончательного отказа.

Выбраны `@hey-api/openapi-ts` 0.99.0 для клиента, моделей, схем и типов обработчиков Fastify, а также Ajv 8.20.0 в режиме 2020 с `ajv-formats` 3.0.1 для runtime-проверки на обеих сторонах. Генератор типов Fastify имеет статус beta; принимаем его использование только для типов ручных обработчиков с проверкой компиляции. OpenAPI 3.1 требует соответствующего диалекта схем; стандартные валидатор и сериализатор Fastify не считаются достаточной проверкой. Используем обычный runtime Ajv, добавляющий код в браузер; автономный ESM-выпуск валидаторов не выбран из-за обнаруженных CommonJS-зависимостей. Backend подключает общие модели, схемы и серверные типы отдельно от браузерного SDK. Совместимость подтверждена узкой пробой на macOS с закреплёнными Node.js, TypeScript и Vite; это не проверка Linux, производственного API, CSP или размера будущего приложения.

Обе операции создания получают случайный UUID в `Idempotency-Key`; область ключа включает вид операции. До отправки ключ и неизменяемые данные сохраняются в `sessionStorage` вкладки; при невозможности сохранить контекст запрос не отправляется. После обновления незавершённая отправка восстанавливается с неизвестным исходом и тем же ключом. Повтор возвращает прежние статус и результат; другой набор данных с тем же ключом не меняет исходную отправку. Окончательность отказа сообщается явно и только после его сохранения по [ADR хранения](0003-booking-storage.md). Это сохраняет гарантию повтора без дубля после потери ответа; отдельно заполненные вкладки независимы, восстановление после закрытия вкладки не обещается.

Моменты времени передаются в UTC, календарные даты относятся к `Europe/Moscow`. Сервер сообщает дату и границы доступности; интерфейс не выводит московское сегодня из часов браузера. Конкретные операции, поля, коды ошибок и порядок списков хранятся в решении вопроса API; реализация и набор новых тестов определяются следующим этапом.
