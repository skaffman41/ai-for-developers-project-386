# SQLite и атомарное подтверждение бронирования

Для основной записи на встречу выбираем SQLite со встроенным `node:sqlite` закреплённого Node.js 24.22.2: один экземпляр backend, одно синхронное соединение и один постоянный локальный файл. Это позволяет обойтись без отдельного сервера БД и совместно сохранять бронирование и результат попытки. Принимаем статус API **Release candidate** и блокировку потока короткими операциями хранения; сетевые обращения и `await` внутри транзакции не допускаются. Основание — [исследование совместимости и гарантий](../research/booking-storage-sqlite.md); решение согласовано в [вопросе выбора хранения](https://github.com/skaffman41/ai-for-developers-project-386/issues/31).

Все пути записи бронирований используют `BEGIN IMMEDIATE`: сначала ищут сохранённый результат попытки, затем, если его нет, заново проверяют тип встречи, действующие правила доступности, текущее время и пересечение полного интервала со всеми бронированиями независимо от типа. Пересечение определяется условием `existing_start < requested_end AND existing_end > requested_start`; соприкасающиеся границы разрешены. Бронирование и успешный результат попытки сохраняются одной транзакцией одного файла. Окончательный отказ также сохраняется до ответа гостю, без бронирования. Повтор возвращает сохранённый результат с проверкой неизменности данных, включая успех после окончания встречи и прежний отказ. Создание типа встречи и результат его повторяемой отправки сохраняются по тому же принципу; одинаковое название не объединяет отправки.

Типы встреч, бронирования и окончательные результаты попыток сохраняются без автоматического удаления или TTL. Горизонт доступных гостю дат не ограничивает историю владельца. Техническая ошибка не становится постоянным бизнес-отказом: если исход записи нельзя надёжно установить или результат отказа не сохранён, клиент сохраняет возможность повторить ту же попытку с неизвестным исходом. Блокировка SQLite сама по себе не означает «Слот уже занят».

Подтверждённые результаты должны переживать штатный перезапуск, аварийную остановку backend и перезагрузку сервера при исправном постоянном диске. Для выбранного одного соединения используем `journal_mode=DELETE`, `synchronous=EXTRA`, `foreign_keys=ON` и ограниченное ожидание блокировки; на macOS также `fullfsync=ON`. Настройки проверяются при открытии. Файл и необходимые SQLite журналы находятся по постоянному локальному пути вне временных и сборочных каталогов; пересборка и установка зависимостей их не удаляют. Гарантия предполагает корректную работу блокировок и синхронизации ОС, файловой системы и диска. Утрата диска, автоматические резервные копии, горизонтальное масштабирование и сетевой файл БД в текущий объём не входят.

Для бесплатного публичного учебного стенда принято отдельное исключение из гарантий долговечности: Railway Free/Trial без постоянного тома использует непостоянную файловую систему, и сброс данных на нём допустим по [ADR 0006](0006-public-demo-deployment.md). Требование постоянного хранения сохраняется для локального размещения с постоянным файлом БД.

Новая пустая БД без демонстрационных типов и бронирований создаётся отдельной явной командой подготовки. Обычный запуск открывает существующий файл по заданному постоянному пути, без автоматического создания замены. Отсутствующий, недоступный, повреждённый файл, чужая или неподдерживаемая схема останавливают запуск до обслуживания HTTP с понятной диагностикой. Поддерживаемые изменения схемы и её версии выполняются транзакционно с сохранением данных; ошибка останавливает запуск. Автоматического сброса и подмены хранилищем в памяти нет.

Для Docker-образа команда подготовки выполняется при сборке, чтобы новый контейнер автоматически стартовал с готовой пустой БД; обычный запуск по-прежнему открывает и проверяет уже существующий файл. Этот способ подготовки и границы сохранности данных бесплатного стенда определены в [ADR 0006](0006-public-demo-deployment.md).

Исследование подтвердило совместимость на macOS arm64 и поведение при падении процесса; выполнение на Linux, нагрузка, авария ОС и ошибки диска разовыми пробами не проверялись. Идентификаторы попыток, HTTP-контракт и восстановление клиентского контекста уточняются в [вопросе API](https://github.com/skaffman41/ai-for-developers-project-386/issues/32); точные имена команды подготовки, параметра пути, схемы и ограниченного timeout относятся к дальнейшему планированию реализации. Новые зависимости, производственный код и тесты этим решением не добавляются.
