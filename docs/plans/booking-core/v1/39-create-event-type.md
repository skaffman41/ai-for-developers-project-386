## Parent

[Основная запись на встречу: типы, бронирование и раздел владельца календаря](https://github.com/skaffman41/ai-for-developers-project-386/issues/37).

## What to build

Владелец календаря создаёт тип в `/owner`, видит его в списке, а гость получает этот же тип через уже работающую запись. Создание полностью проходит общий контракт и постоянное хранение, безопасно повторяется после потери ответа и восстанавливается после обновления той же вкладки. Этот срез вводит переиспользуемые гарантии повторяемой отправки, которые затем использует бронирование.

## Acceptance criteria

- [ ] `/owner` доступен напрямую и после reload, в шапке есть «Владельцу календаря», доступен переход на `/booking`. Реализована область «Типы встреч» с формой, списком и пустым состоянием; список бронирований добавляется отдельным срезом. Входа и проверки прав нет.
- [ ] `POST /api/event-types` включён в общий OpenAPI и всю производную/runtime-цепочку. Название 1–100 после trim, целая длительность 1–540, описание до 2000; ограничения строк/необязательного описания соблюдены. Неверные JSON-типы и лишние поля отклоняются без приведения, сырая длина до trim не подменяет согласованные пределы.
- [ ] Новый тип имеет устойчивые id/displayCode и определённый порядок, одинаковые названия разрешены. После успеха один тип виден в списке и доступен гостю, форма очищена, есть сообщение. При отказе ввод сохранён; ошибки связаны с полями и фокусом. До отправки объяснена невозможность изменения/удаления.
- [ ] Ключ UUID и исходные данные сохраняются в sessionStorage до POST; при невозможности записи запрос отсутствует. Поля блокируются на отправке/неизвестном исходе, повтор использует ту же отправку. После reload она восстанавливается. Известный результат очищает контекст; успех очищает форму, отказ сохраняет ввод. Обновление списка не сбрасывает ввод и не прерывает отправку.
- [ ] В SQLite сущность и результат сохраняются атомарно; окончательный отказ сохраняется без сущности. Сохранённый повтор возвращает прежние статус/тело. Другие данные с тем же ключом дают конфликт, исходный результат не изменяется; перестановка ключей JSON не считается изменением, нормализация не скрывает реальную замену значений. Отдельные отправки одинакового названия независимы.
- [ ] Потерянный/непригодный ответ, несохранённый отказ и технические сбои остаются неизвестным исходом: «Не удалось узнать результат создания типа», «Повторить создание». Не возникает второго типа. Клиент не завершает отправку по чужому ключу. Блокировка SQLite не выдаётся за бизнес-отказ, нет повторного выполнения внутри оставшейся активной транзакции после ошибки commit.
- [ ] Принятый жизненный цикл результатов без TTL подтверждён HTTP/процессными проверками: конкурентный повтор, сохранённый отказ, штатный restart и синхронизированная остановка до/после commit с тем же файлом; нет частично созданного результата. Поддерживаемое изменение схемы сохраняет предыдущие данные/версию либо откатывается целиком.
- [ ] Playwright с настоящим backend проверяет создание → чтение гостем, ошибки/пустые состояния, оба случая потерянного ответа, некорректный ответ, reload, отказ sessionStorage до POST и ошибки локального сохранения результата. Клавиатура/320/1440 px проверены для новых элементов; полный check успешен.

## Testing Decisions

T2, T4–T8 родителя применительно к типам; вклад в AC1, AC3, AC5–AC11. Механизм тестовых сбоев и контролируемых стадий commit не открывает служебных HTTP-маршрутов продукта. Статусы/outcome и raw payload сравниваются по принятому контракту.
