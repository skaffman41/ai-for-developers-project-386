[Основная запись на встречу: типы, бронирование и раздел владельца календаря](https://github.com/skaffman41/ai-for-developers-project-386/issues/37).

## What to build

Настроить проверяемый выпуск одной версии всего приложения через release-please: Conventional Commits формируют Release PR с версией/changelog; его явный ручной merge приводит к тегу и GitHub Release. Самостоятельных npm-выпусков workspaces и развёртывания нет. Дополнение объёма прямо запрошено пользователем при вызове to-tickets 2026-11-09 и имеет приоритет над прежним исключением автоматического выпуска из спецификации. Родительский текст этим проходом не переписывается.

## Acceptance criteria

- [ ] Одна единица выпуска для всего приложения, стратегия simple в manifest-конфигурации, отдельная версия приложения и changelog; первый предлагаемый выпуск 0.1.0, теги vX.Y.Z. Начальная версия и граница истории заданы явно и согласованно; за основу диапазона реализации берётся подтверждённая база планирования. Повторный запуск не создаёт дубль Release PR/тега/релиза.
- [ ] Action и средства проверки закреплены совместимыми версиями/полными SHA. Release PR поддерживается на main по Conventional Commits, automerge отсутствует; после отдельно разрешённого ручного merge создаются соответствующие тег и GitHub Release. npm publish, контейнеры и deployment не подключаются.
- [ ] Применяется встроенный GITHUB_TOKEN с явными необходимыми job permissions. Сохранён стандартный default read для прочих workflow. В настройке репозитория включается необходимое разрешение Actions создавать PR; учётные данные из локального gh не копируются в secrets. Необходимость изменения настройки выявлена read-only проверкой: сейчас can_approve_pull_request_reviews=false.
- [ ] После создания/обновления Release PR явно запускается существующий app-check через workflow_dispatch для release-ветки, с привязкой результата к её актуальному SHA. Возможная необходимость одобрения автоматических pull_request-запусков не подменяет успешную проверку. Успех проверки старого SHA не считается проверкой обновлённого PR.
- [ ] В общий check включена проверка release-конфигурации по схеме закреплённого инструмента. На управляемой тестовой истории/разовом dry-run проверяются вычисление версии и changelog, начальный диапазон, повтор без дубля и отсутствие публикации при проверке. Подготовка конфигурации и dry-run не создают реальных Release PR/тегов/релизов.
- [ ] Документированы включение, необходимая настройка прав, ручной merge Release PR и способ проверить результаты. После отдельно разрешённой публикации проверяются реальный запуск Actions и app-check на точном SHA Release PR; неподтверждённый удалённый запуск не объявляется успешным. Фактическая публикация и первый выпуск остаются отдельными явно разрешаемыми действиями по workflow проекта.
- [ ] Защищённый workflow Hexlet не изменён; локальный полный check успешен, конфигурация прошла необходимые Standards/Spec review. Настройка не требует готовности функции записи и проверяема независимо от неё.

## Testing Decisions

Это прямое дополнение текущего запроса пользователя к охвату родителя. Проверки конфигурации и dry-run являются частью данного среза; успешный app-check Release PR подтверждается только на его реальном SHA после разрешённой публикации. Проверка конфигурации не выдаётся за уже состоявшийся выпуск.

Основания: [release-please Action](https://github.com/googleapis/release-please-action), [manifest и bootstrap](https://github.com/googleapis/release-please/blob/main/docs/manifest-releaser.md), [dry-run CLI](https://github.com/googleapis/release-please/blob/main/docs/cli.md), [GitHub workflow triggers](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow). Текущая документация GitHub разрешает workflow_dispatch от GITHUB_TOKEN; автоматические PR-запуски могут ожидать одобрения. Настройка явного dispatch проверяет цепочку независимо от этого.
