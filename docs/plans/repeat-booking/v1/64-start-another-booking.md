## Parent

[Повторная запись из подтверждения бронирования — #63](https://github.com/skaffman41/ai-for-developers-project-386/issues/63)

## What to build

Дать гостю возможность после успешного бронирования нажать «Записаться ещё раз», пройти новый путь с пустого выбора типа встречи и подтвердить вторую встречу в той же вкладке. Первое бронирование остаётся у владельца календаря; прежнее подтверждение восстанавливается до явного начала новой записи, а затем заменяется результатом следующего успешного бронирования.

Включить в тот же результат обработку ошибки локального сброса, клавиатурное управление, сохранение гарантий неизвестного исхода и один согласованный браузерный сценарий с настоящим сервером. Задача покрывает AC1–AC8 спецификации #63 целиком и демонстрируется двумя сохранёнными встречами в списке владельца календаря.

## Acceptance criteria

- [ ] На успешном подтверждении есть доступная мышью и клавиатурой кнопка «Записаться ещё раз». Она доступна при ширинах 320 и 1440 px; после начала нового пути фокус переводится к его первому шагу. Покрывает AC1 и часть AC3.
- [ ] До нажатия кнопки перезагрузка и возвращение через главную к записи в той же вкладке восстанавливают прежнее подтверждение с теми же сведениями и не создают новых бронирований. Покрывает AC2.
- [ ] Успешное нажатие открывает выбор типа встречи без прежнего типа, даты и слота; имя и email пусты, старые ошибки и контекст завершённой попытки не возвращаются, в том числе после ранее восстановленной отправки. Доступность следующей встречи запрашивается заново по действующим правилам. Покрывает AC3 и часть AC6.
- [ ] После успешного начала новой записи перезагрузка или возвращение к записи больше не восстанавливают прежнее подтверждение. Само нажатие не создаёт, не отменяет и не удаляет бронирования; первая запись остаётся у владельца календаря. Покрывает AC4.
- [ ] При ошибке сброса гость остаётся на прежнем подтверждении и получает понятное сообщение; ложный переход к пустой форме и запрос создания отсутствуют. После устранения причины действие можно повторить. Покрывает AC5.
- [ ] Во время отправки и при неизвестном исходе нельзя начать новую запись вместо выяснения результата. Безопасный повтор сохраняет прежние ключ и данные. Новая отправка после завершённого успеха получает собственный ключ и не использует прежнюю попытку. Существующие серверные гарантии конфликтов и идемпотентности сохраняются. Покрывает AC6.
- [ ] Добавлен ровно один согласованный браузерный сценарий: первая запись, восстановление подтверждения после перезагрузки и возвращения через главную, новая запись через кнопку с очищенными выборами и контактами, вторая успешная запись, обе реальные записи у владельца календаря с сопоставлением идентификаторов и данных. Ответы API бронирования в успешном пути не подменяются; новое подтверждение соответствует второй записи. Покрывает AC7 и подтверждает AC2–AC4.
- [ ] Пройдён существующий полный `mise run check`, включая новый сценарий; смысл существующих проверок восстановления, неизвестного исхода, локальных ошибок и безопасных повторов сохранён. Выполнены независимые Standards/Spec review и необходимые исправления. Локальная готовность и удалённый CI опубликованного результата различаются в отчёте. Покрывает AC8.
- [ ] В отчёте приведены результаты наблюдения ошибки сброса, повторного действия после восстановления доступа, отсутствия новых запросов при сбросе, клавиатурного пути и просмотра на 320/1440 px. Нужные снимки и журналы сохранены вне репозитория. Подтверждает AC1, AC5 и AC8.
- [ ] Сохранены действующие HTTP-контракт, серверные правила и данные бронирований. Не изменён защищённый workflow Hexlet, не переписаны исторические снимки плана; исправление CI #62 не реализовано повторно. Результат сохранён отдельным локальным Conventional Commit со ссылкой на эту задачу и полным Answer; до отдельно разрешённого merge задача остаётся открытой.

## Testing Decisions

- Пользователь прямо разрешил один новый браузерный сценарий в принятом Q6 обсуждения `grill-with-docs`; повторное согласование тех же границ не требуется.
- Использовать существующую высокую границу Playwright Chromium: настоящие frontend и backend, изолированная файловая SQLite и управляемое серверное время. Проверять доступные действия и фактически сохранённые записи, а не способ сброса состояния или имена внутренних компонентов. Новые тестовые HTTP-маршруты и дополнительные заглушки не вводятся.
- Образцы — существующая проверка подтверждения с перезагрузкой и сквозной путь «владелец → гость → владелец» с сопоставлением реального ответа создания и списка владельца. Новый сценарий использует ту же гостевую вкладку для обеих записей и не требует сохранения ещё не отправленного черновика при обновлении страницы.
- Выполнить существующие проверки неизвестного исхода, восстановления и безопасных повторов без ослабления утверждений, а затем полный `mise run check`.
- Ошибку сброса подтверждения наблюдать с управляемым сбоем локального хранилища по существующему образцу: прежний экран и данные сохраняются, ошибка понятна, запрос создания не отправлен, после восстановления доступа действие повторяется. Отдельный новый автотест для этого наблюдения не требуется. Дополнительные новые unit- и HTTP-тесты не добавляются.
- Новую кнопку и начало первого шага проверить клавиатурой и на ширинах 320/1440 px в пределах существующего визуального просмотра. Снимки и наблюдения хранить вне репозитория.

## Scope notes

Полный сброс состояния выполняется внутри этой вертикальной задачи; отдельного предварительного рефакторинга не требуется. В объём не входят архив подтверждений, отмена или перенос встреч, письма, сохранение прежних контактов для новой записи, изменения API или БД. Публикация кода, создание PR, merge и развёртывание требуют отдельных явных команд. Готовый локально результат #62 остаётся самостоятельной работой и не является функциональным блокером этой задачи.
