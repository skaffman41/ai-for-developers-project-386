# Скиллы и агентная среда: GitHub Issues workflow

## Problem Statement

Шаг 3 Hexlet требует GitHub Issues, но текущая конфигурация направляет агента в локальный Markdown-трекер. История этапа 2 уже содержит одну завершённую спецификацию и шесть завершённых задач. Нужны сохранение этой истории, воспроизводимая подготовка Codex и короткие команды с определёнными полномочиями.

## Solution

GitHub Issues репозитория `skaffman41/ai-for-developers-project-386` становится основным трекером карт решений, спецификаций и задач. Семь исторических документов импортируются как закрытые Issues с сохранением источников, результатов, истории и зависимостей. Локальный трекер сохраняется неизменяемым архивом.

Согласованный план сохраняется в Git отдельным коммитом до реализации. Снимок содержит тексты спецификации и задач, их номера, зависимости, критерии и решения о проверках. Статусы и обсуждение ведутся в GitHub; изменение согласованного объёма требует новой версии снимка.

## User Stories

1. Как сопровождающий, я хочу открыть историю этапа 2 через Issues и проверить её по исходным документам и Git-коммиту.
2. Как пользователь Codex в WebStorm и CLI, я хочу вызвать инженерный скилл короткой командой в новом сеансе.
3. Как пользователь, я хочу запускать один тикет через `$implement <issue>` или весь согласованный граф через `$implement-spec <spec>`.
4. Как пользователь, я хочу получать локальные коммиты и отчёты без повторных вопросов о разрешённых действиях.
5. Как сопровождающий, я хочу отдельно разрешать push, создание PR и merge.
6. Как агент, я хочу различать готовность результата в интеграционной ветке и завершение после merge в основную ветку.
7. Как сопровождающий, я хочу воспроизвести проверенную установку глобальных Matt Pocock Skills без изменения их исходных процедур.

## Implementation Decisions

- Целевая среда — Codex в WebStorm с поддержкой Codex CLI. Скиллы Мэтта остаются глобальными; проект фиксирует проверенную ревизию и процедуру подготовки.
- Используется закреплённый GitHub CLI через mise. Репозиторий проверяется перед первой записью; операции явно адресуются репозиторию пользователя.
- Стандартные роли triage сохраняются. Категории `bug` и `enhancement` отделены от состояния triage и от выполнения.
- `$implement` выполняет ровно один тикет в рабочей ветке. `$implement-spec` выполняет согласованный граф в интеграционной ветке через подагентов в отдельных worktree. Каждый результат задачи фиксируется отдельным Conventional Commit.
- Эти команды разрешают назначение выбранных Issues и публикацию отчётов. Push, создание PR и merge требуют отдельных явных команд.
- Issues реализации остаются открытыми до merge PR в `main`. В рамках одного запуска графа проверенный результат в интеграционной ветке разблокирует зависимые задачи. Вне этой ветки требуется merge. Закрытие без успешного выполнения не разблокирует зависимость.
- Исследования и решения закрываются после принятого результата; PR с кодом для них не обязателен.
- Независимое code-review выполняется для существенных изменений. Существующие пользовательские границы тестирования сохраняются.
- Проверки приложения запускаются на push и pull request. Предоставленный Hexlet workflow сохраняется побайтово.
- Новые спецификации и задачи публикуются в GitHub. Повторная миграция находит существующие записи по устойчивым маркерам, исключая дубли.

## Testing Decisions

Новые автоматические тесты не добавляются. Используются существующие `mise run check`, `git diff --check`, проверка ссылок и содержимого документов. Миграция проверяется чтением GitHub API: содержимое, причины закрытия, связи, источники, отсутствие дублей. Глобальные скиллы и локальный архив сравниваются с исходными хешами.

Отдельный свежий сеанс Codex в режиме чтения должен назвать трекер, репозиторий, команду проверок и полномочия обоих режимов, обнаружить скиллы и прочитать связанную спецификацию с зависимостями. Проверка в WebStorm подтверждает доступность ручных команд. Неподтверждённые части проверки явно остаются незавершёнными.

## Acceptance Criteria

- [ ] AC-01: семь исторических документов представлены закрытыми Issues с результатами, историей, источником и соответствием старых ID новым номерам.
- [ ] AC-02: архив этапа 2 побайтово совпадает с исходным коммитом `6e03736e19494b99ca40a4e64e076145b37b7941`; повторная миграция не создаёт дубли.
- [ ] AC-03: инструкции направляют все новые карты, спецификации и тикеты в GitHub Issues нужного репозитория; метки triage и категории определены и существуют.
- [ ] AC-04: документированы разрешение номеров/URL/исторических ID, чтение полной задачи и спецификации, связи родителя и блокирующих задач.
- [ ] AC-05: оба режима реализации работают с ветками, локальными коммитами и отчётами; публикация кода требует отдельной команды.
- [ ] AC-06: описаны закрытие после merge, готовность внутри интеграционной ветки, отказанные зависимости и отдельное завершение задач решений.
- [ ] AC-07: план зафиксирован отдельным коммитом до изменения конфигурации проекта; определены новые версии снимков при изменении требований.
- [ ] AC-08: gh закреплён для macOS arm64 и Linux x64; ревизия всех 38 глобальных Matt Pocock Skills проверена, установка воспроизводима, исходные скиллы не изменены.
- [ ] AC-09: свежий сеанс Codex и проверка WebStorm подтверждают обнаружение скиллов и чтение конфигурации; результаты обеих проверок сохранены.
- [ ] AC-10: существующий `mise run check` проходит, app-check включает pull request, Hexlet workflow неизменен, push/PR/merge не выполнены.

## Out of Scope

Функциональность календаря, новые автоматические тесты, OpenSpec, перенос личных предпочтений в общие инструкции, настройка других агентов, переустановка или редактирование глобальных скиллов, публикация ветки, создание PR, merge и изменение защиты GitHub.

## Approval

Пользователь согласовал восемь решений в диалоге и затем явно подтвердил итоговый вариант и выполнение всего объёма. Разрешены создание Issues, изменение согласованных файлов и локальные коммиты. Подготовка gh для публикации этого плана является bootstrap-предпосылкой; конфигурация проекта меняется после planning-коммита.
