## Problem Statement

Автор учебного проекта «Календарь звонков» имеет готовую локальную Docker-версию, но пока не может передать проверяющему публичную ссылку на работающий сервис. Без этого нельзя завершить шаг 7 Hexlet и показать сценарии гостя и владельца календаря вне компьютера разработчика.

Приложение уже использует SQLite и требует заранее подготовленный файл БД. В #56 уже подготовлены единый сервер frontend/API и Docker-образ. Публичная приёмка и управление выбранным хостингом ещё не подтверждены.

## Solution

Сохранить подготовленный единый Docker-образ и бесплатно разместить учебный стенд на Railway в пределах Free/Trial-кредитов. Один процесс Fastify обслуживает frontend и API по одному публичному адресу, а новый контейнер автоматически стартует с пустой SQLite-базой, подготовленной при сборке образа. Первоначальная публикация и обновления выполняются через MCP Railway по явной команде после объединения изменений в основную ветку.

Публичный стенд предназначен для вымышленных имён и email. Раздел владельца календаря остаётся доступен без входа. Ради бюджета 0 ₽ принимается сброс данных после засыпания сервиса, перезапуска и нового деплоя; локальное размещение с постоянным хранилищем сохраняет прежние гарантии долговечности.

### Критерии приёмки

- **AC1. Сборка образа.** В корне репозитория есть Dockerfile, по которому из чистого checkout собирается Linux-образ полного приложения. Образ включает собранные frontend и backend, необходимые runtime-зависимости и подготовленную пустую SQLite-базу. Для сборки и запуска не нужны локальные данные разработчика, его БД, OAuth-сессии или секреты.
- **AC2. Автоматический запуск.** Запуск нового контейнера из образа автоматически поднимает приложение без дополнительной ручной команды подготовки БД. Сервис доступен извне контейнера по порту из переменной окружения PORT. В контейнере используется один процесс Fastify, который обслуживает frontend и API; отдельный Vite-сервер или процесс раздачи статики не требуется.
- **AC3. Единая точка входа.** Через один адрес работают главная страница, прямое открытие и обновление `/booking` и `/owner`, ресурсы frontend, действующий API и `/health`. API продолжает возвращать контрактные ответы, включая ошибки; возврат страницы приложения для клиентских маршрутов не подменяет ответы API.
- **AC4. Подготовка и проверка SQLite.** Пустая БД с актуальной схемой явно создаётся при сборке образа. В новом контейнере отсутствуют демонстрационные типы встреч и бронирования. Обычный запуск открывает и проверяет подготовленный файл; отсутствие, недоступность, повреждение или неподдерживаемая схема останавливают запуск без автоматической подмены новой БД. Права runtime-пользователя позволяют SQLite изменять файл и создавать необходимые журналы.
- **AC5. Локальная сохранность.** При локальном запуске с явно подготовленным постоянным файлом или томом БД данные сохраняются после перезапуска и пересоздания контейнера с тем же хранилищем. Пересборка образа не заменяет этот файл. Существующие гарантии хранения для такого размещения сохраняются.
- **AC6. Бесплатный публичный сервис.** На Railway опубликован Docker-вариант приложения с одним экземпляром backend и непостоянной файловой системой. Приложение отвечает по публичной ссылке и использует выданный платформой PORT. Используются только доступные бесплатные Free/Trial-кредиты с бюджетом 0 ₽; тариф и остаток подтверждаются в выбранном аккаунте. Платная подписка, платные ресурсы, постоянный том и внешняя БД не создаются. Исчерпание бесплатного лимита остаётся блокировкой, а не разрешением на расходы.
- **AC7. Управление через MCP.** В репозитории есть безопасный шаблон подключения официального MCP Railway с воспроизводимой инструкцией. Авторизация выполняется документированным способом без секретов в Git. Реальным чтением подтверждены аккаунт и доступные проекты/сервисы, фактический каталог позволяет подготовить первоначальную публикацию и последующие ручные обновления. Для выкладки сохранены результат MCP-операции и проверка сервиса. Документация или успех CLI сами по себе не заменяют подтверждение MCP.
- **AC8. Явное обновление.** Деплой выполняется по отдельной команде после включения нужной версии в основную ветку. Автоматическая выкладка приложения отключена; изменение репозитория и локальной конфигурации само по себе не применяет изменения платформы и не сбрасывает данные. Любые отложенные изменения конфигурации и их применение входят только в явно разрешённую выкладку.
- **AC9. Сценарии по публичной ссылке.** Владелец календаря создаёт тип встречи, гость бронирует будущий свободный слот с вымышленными контактами, а владелец видит бронирование в списке. Другая попытка бронирования пересекающегося полного интервала получает контрактный отказ «Слот уже занят» и не создаёт вторую встречу. Повтор той же попытки с тем же ключом сохраняет действующую семантику повтора в пределах текущей БД.
- **AC10. Пустое состояние и сброс.** Новый контейнер из того же образа без подключённого постоянного хранилища начинает работу с пустыми списками типов встреч и бронирований. Учебный стенд сохраняет атомарность бронирования и обработку повторных отправок в пределах текущей БД, но не обещает сохранение типов встреч, бронирований и результатов попыток после её сброса.
- **AC11. Документация запуска и доступа.** README содержит публичную ссылку, порядок сборки и запуска контейнера с PORT, подключения и авторизации MCP Railway без секретов, ручной выкладки и подготовки локального постоянного хранилища. Явно описаны учебное назначение с вымышленными данными, открытый раздел владельца, допустимая потеря SQLite при замене контейнера и ограничения фактически выбранных Free/Trial-кредитов. Если включено засыпание, описаны его действительные условия и задержка пробуждения; ограничения Render не приписываются Railway.
- **AC12. Секреты и конфигурация.** Опубликованная проектная конфигурация и образ не содержат реальных ключей, токенов, OAuth-сессий или локальной рабочей БД. История репозитория проверена на секреты; результат проверки зафиксирован без раскрытия найденных значений. Шаблоны и инструкция позволяют повторить подключение из отдельного окружения.
- **AC13. Сохранение готового поведения.** Проходит существующий полный `mise run check`, включая проверки API-контракта, сборку, HTTP-проверки и Playwright. Публичные правила доступности, запрет пересечений, контракт API и прежнее поведение локального постоянного хранения сохраняются с явно описанным исключением для бесплатного стенда. Новые тесты не добавляются. Защищённый workflow проверки Hexlet сохраняется без изменений.
- **AC14. Проверяемая приёмка.** Отчёт связывает проверенные исходники и образ с локальными командами сборки и запуска, результатами существующих проверок, публичным URL и доказательствами сценариев и конфликта. Различаются локальная готовность Docker-части и фактически состоявшийся деплой: успех локальных проверок не подменяет публичную приёмку.

## User Stories

1. Как автор учебного проекта, я хочу собрать приложение в Docker-образ, чтобы воспроизвести запуск вне моего компьютера.
2. Как проверяющий проекта, я хочу найти Dockerfile в корне репозитория, чтобы собрать приложение предусмотренным способом.
3. Как проверяющий проекта, я хочу запустить контейнер одной командой, чтобы приложение автоматически начало обслуживать запросы.
4. Как сопровождающий проекта, я хочу задавать порт через PORT, чтобы один образ работал локально и на хостинге.
5. Как автор учебного проекта, я хочу публиковать приложение бесплатно, чтобы завершить учебный этап без расходов на инфраструктуру.
6. Как сопровождающий проекта, я хочу видеть явно выбранный бесплатный тариф, чтобы конфигурация соответствовала нулевому бюджету.
7. Как сопровождающий проекта, я хочу обслуживать frontend и API одним сервисом, чтобы выкладывать приложение как единое целое.
8. Как гость, я хочу открыть публичную ссылку без установки приложения, чтобы записаться на встречу через браузер.
9. Как гость, я хочу открыть `/booking` по прямой ссылке, чтобы сразу перейти к записи на встречу.
10. Как гость, я хочу обновить страницу записи, чтобы браузер снова открыл работающий интерфейс.
11. Как владелец календаря, я хочу напрямую открыть и обновить раздел управления, чтобы пользоваться им по самостоятельной ссылке.
12. Как владелец календаря, я хочу увидеть пустое состояние нового стенда, чтобы начать с создания своего типа встречи.
13. Как владелец календаря, я хочу создать тип встречи на публичном стенде, чтобы гости могли выбрать его для бронирования.
14. Как гость, я хочу выбрать тип встречи, дату и свободный слот по действующим правилам, чтобы забронировать подходящий интервал.
15. Как гость, я хочу указать вымышленные имя и email на учебном стенде, чтобы проверить запись без использования реальных контактов.
16. Как гость, я хочу видеть подтверждение успешного бронирования, чтобы понимать результат отправки.
17. Как владелец календаря, я хочу видеть публично созданное бронирование в своём списке, чтобы подтвердить сквозную работу сервиса.
18. Как гость, я хочу получить понятный отказ при занятом интервале, чтобы выбрать другой свободный слот.
19. Как владелец календаря, я хочу сохранить запрет пересечений между встречами разных типов, чтобы не получить двойную запись.
20. Как гость, я хочу безопасно повторить ту же попытку в пределах текущей БД, чтобы потеря ответа не создала дублирующее бронирование.
21. Как автор учебного проекта, я хочу явно описать открытый доступ к разделу владельца, чтобы посетители понимали назначение демонстрации.
22. Как посетитель стенда, я хочу знать о возможном сбросе учебных данных, чтобы не рассчитывать на их постоянное хранение.
23. Как посетитель стенда, я хочу знать о задержке пробуждения бесплатного сервиса, чтобы понимать возможное ожидание первого ответа.
24. Как сопровождающий проекта, я хочу получать готовую пустую БД в новом образе, чтобы не готовить её вручную перед каждым новым контейнером.
25. Как сопровождающий проекта, я хочу получать ошибку при повреждённой или отсутствующей БД, чтобы обычный запуск не скрывал проблему созданием замены.
26. Как локальный пользователь, я хочу подключать постоянное хранилище, чтобы сохранять данные между перезапусками и пересозданиями контейнера.
27. Как сопровождающий проекта, я хочу управлять выкладкой через MCP, чтобы агент мог выполнить публикацию предусмотренным заданием способом.
28. Как сопровождающий проекта, я хочу подключить MCP по безопасной инструкции, чтобы повторить настройку без добавления секретов в репозиторий.
29. Как сопровождающий проекта, я хочу выбирать момент выкладки явной командой, чтобы контролировать обновление стенда и сброс его данных.
30. Как проверяющий проекта, я хочу найти публичную ссылку и инструкции в README, чтобы открыть сервис и повторить его запуск.
31. Как рецензент, я хочу увидеть результаты существующих проверок и отдельной публичной приёмки, чтобы отличать проверку исходников от проверки опубликованного приложения.
32. Как автор учебного проекта, я хочу сохранить существующую реализацию бронирования и генерацию контракта, чтобы упаковка и деплой не меняли согласованные правила сервиса.

## Implementation Decisions

- Архитектура публикации — один Docker-контейнер, один экземпляр backend и один процесс Fastify, обслуживающий собранный frontend и действующий API по одному адресу. Дополнительный сервер frontend в runtime не вводится.
- Модуль HTTP-сервера получает раздачу статических ресурсов и обработку прямых клиентских маршрутов. API и проверка здоровья сохраняют свои контрактные пути, методы, статусы и форматы ответов. Обработка клиентских маршрутов отделена от обработки API.
- Сборка образа использует закреплённую в проекте версию Node.js и действующую цепочку сборки приложения и контракта. Среда выполнения контейнера содержит необходимые runtime-зависимости и доступные для записи файл SQLite и каталог его журналов.
- Контейнерный запуск слушает все необходимые сетевые интерфейсы и порт из PORT. DATABASE_PATH по умолчанию указывает на подготовленный в образе файл; явный путь позволяет использовать отдельно подготовленное постоянное локальное хранилище.
- Пустая SQLite-база с текущей схемой создаётся существующей явной командой подготовки при сборке. Обычный запуск сохраняет проверку существования, доступности и схемы файла и остановку при непригодном хранилище. Автоматическое восстановление повреждённого файла или молчаливое создание замены не вводится.
- По прямой команде пользователя 2026-11-11 вместо Render используется запасной Railway из задания Hexlet. Выбран один Docker-сервис без постоянного тома и внешней БД, бюджет 0 ₽ в пределах доступных Free/Trial-кредитов. Тариф и лимиты фактического аккаунта проверяются до создания ресурсов; платный переход не выполняется. Потеря SQLite при пересоздании контейнера и новом деплое допустима; сохранение после сна или перезапуска без постоянного тома не обещается. Для локального постоянного хранения прежние гарантии сохраняются.
- Публичная версия остаётся учебной демонстрацией с вымышленными контактами и доступным без входа разделом владельца календаря. Добавление авторизации и работа с реальными контактами не входят в этот этап.
- Первоначальная публикация и обновления выполняются через официальный MCP Railway по явной команде после объединения выбранной версии в основную ветку. Автоматический деплой выключен. Подготовленный шаблон или локальная конфигурация не применяются автоматически; параметры сервиса и отложенные изменения перед выкладкой проверяются отдельно.
- Конфигурация подключения MCP Railway поставляется как безопасный проектный шаблон с инструкцией. Авторизация через браузер допустима; сессионные данные и реальные секреты остаются в пользовательском окружении. Доступ Railway к нужной версии исходного репозитория проверяется отдельно от авторизации MCP.
- Схема данных, операции API, TypeSpec как исходник контракта, генерация производных, правила доступности, обработка конфликтов и повторов сохраняются. Изменения модулей ограничены упаковкой, серверной раздачей приложения, настройкой окружения публикации и документацией согласованных ограничений.
- Недоступность нужной операции MCP или бесплатного лимита не разрешает платную подписку либо публикацию другим каналом под видом MCP. Фактические возможности подключённого сервера проверяются до создания ресурса.

## Testing Decisions

- **T1. Согласование.** 10 ноября 2026 года пользователь подтвердил предложенную границу проверок ответом «Да, такие проверки подходят»: существующий полный прогон, разовая проверка Docker-контейнера и публичного Render-сервиса, проверка нового пустого контейнера и локального постоянного хранения. Новые тесты не добавляются. 11 ноября пользователь прямо поручил использовать Railway MCP как альтернативу Render; остальные границы проверок сохранены.
- **T2. Основная граница.** Проверяется внешнее поведение полного приложения через браузер и HTTP, а не устройство Docker-слоёв, внутренние функции или выбранный способ подключения статики. Тот же пользовательский сценарий проверяется сначала на собранном контейнере, затем по публичному адресу с настоящим backend и SQLite, без подмены ответов API бронирования.
- **T3. Существующий образец.** В проекте уже есть браузерный сценарий пустого календаря «владелец → гость → владелец», HTTP-проверки конкурентных пересечений, повторов, соседних границ и поведения SQLite. Они служат образцом ожидаемого внешнего поведения и входят в существующие проверки. Текущие Playwright fixtures запускают отдельный локальный backend и Vite preview, поэтому их успех сам по себе не доказывает работу production-контейнера или Railway. Автоматическое перенаправление всего набора на публичный стенд в этот объём не входит.
- **T4. Регрессии.** На итоговом результате выполняется существующий `mise run check`: версии, форматирование, линтер, генерация и проверка контракта, типы, сборка, HTTP-проверки, Playwright и проверка локальных хуков. Прошлые успешные запуски не объявляются результатом изменённого приложения.
- **T5. Контейнер.** Образ собирается из чистого checkout и запускается без ручной подготовки БД. Проверяются доступ извне контейнера, PORT с непредположенным значением, `/health`, ресурсы frontend, прямое открытие и обновление клиентских маршрутов, корректные ответы API и полный сценарий бронирования. Новый отдельный контейнер из того же образа без постоянного тома имеет пустые списки.
- **T6. Постоянное хранилище и ошибки.** На изолированных локальных данных проверяется сохранность типа встречи и бронирования после перезапуска и пересоздания контейнера с тем же явно подготовленным постоянным хранилищем. Отдельная разовая проверка отсутствующего или повреждённого файла подтверждает остановку запуска без создания замены. Рабочая БД разработчика и данные публичного стенда для этих проверок не используются.
- **T7. Публичная приёмка.** По адресу Railway создаётся тип встречи, выбирается реально доступный будущий слот, подтверждается бронирование с вымышленными контактами и проверяется список владельца календаря. Две разные попытки на пересекающиеся интервалы приводят к одному успеху и контрактному отказу второй попытки, а не к двум бронированиям. Повтор того же ключа отличается от другой попытки и проверяется в рамках действующих правил идемпотентности. Фиксированные часы локальных fixtures не переносятся на публичный сервис.
- **T8. Деплой и документация.** Проверяются фактический аккаунт Railway, бесплатный Free/Trial-лимит, отключённые автоматические обновления, воспроизводимость MCP-подключения, доступ к исходникам, публичная ссылка и ограничения хранения. Проверка истории и образа на секреты не раскрывает значения. У документов проверяются ссылки и форматирование, включая `git diff --check`. Условия Render (15 минут и около минуты) не используются как доказательство поведения Railway.
- **T9. Доказательства и пределы.** Отчёт содержит проверенный commit, идентификатор образа, команды, коды завершения, результаты сценариев, время публичной проверки и URL; отдельно отмечаются непроверенные критерии. Авторизация, отсутствие необходимой MCP-возможности или неудавшаяся публичная приёмка не маскируются успешным локальным прогоном. Новые тестовые файлы, тестовые случаи, моки и тестовая инфраструктура требуют отдельного прямого запроса пользователя.

## Out of Scope

- Платные тарифы Railway, покупка кредитов, постоянный том, внешняя БД и другой хостинг в качестве автоматического обхода. Разрешённая пользователем замена Render на Railway входит в эту версию.
- Гарантия сохранности данных бесплатного публичного стенда после сна, перезапуска или деплоя; внешнее постоянное хранилище, резервное копирование и восстановление потерянного диска.
- Несколько экземпляров backend, горизонтальное масштабирование, отдельные сервисы frontend и API.
- Авторизация, несколько владельцев календаря, реальные контактные данные на демонстрационном стенде, уведомления и внешние календари.
- Изменение публичного API, схемы БД, правил доступности, запрета пересечений или бизнес-семантики повторов в пределах текущей БД.
- Демонстрационные типы встреч и бронирования в образе, автоматическая подмена повреждённого или пропавшего файла БД.
- Новые тесты без отдельного запроса пользователя, замена тестовых фреймворков и автоматизация всего браузерного набора против Railway.
- Изменение защищённого workflow Hexlet, переписывание истории Git, переработка ранее завершённых этапов и новый функциональный дизайн интерфейса.
- Создание инфраструктуры, реализация, push, PR, merge, выпуск новой версии или отметка завершения шага в Hexlet в рамках одной лишь публикации этой спецификации.
