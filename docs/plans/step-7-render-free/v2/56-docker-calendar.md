## Parent

[Спецификация #55 — Шаг 7: Docker и бесплатный публичный стенд на Railway](https://github.com/skaffman41/ai-for-developers-project-386/issues/55).

## What to build

Автор проекта запускает полный календарь одной командой из собранного Docker-образа: владелец календаря создаёт тип встречи, гость бронирует свободный слот, а владелец видит результат по тому же адресу. Новый контейнер уже содержит подготовленную пустую SQLite-базу. Локальное подключение отдельно подготовленного постоянного хранилища сохраняет данные при перезапуске и пересоздании контейнера.

Это законченная локальная версия будущего публичного сервиса. Сборка, подготовка БД, сетевой запуск, frontend, API и проверка пользовательского сценария входят в одну задачу.

## Acceptance criteria

- [ ] Из чистого checkout по корневому Dockerfile собирается Linux-образ полного приложения на закреплённой версии Node.js, без локальной БД разработчика и секретов.
- [ ] Новый контейнер автоматически запускает один процесс Fastify без ручной подготовки БД и доступен извне по PORT, в том числе при непредположенном значении порта.
- [ ] По одному адресу работают frontend, его ресурсы, `/health`, API, прямое открытие и обновление `/booking` и `/owner`. API-ошибки сохраняют контрактный формат и не подменяются страницей приложения.
- [ ] Пустая SQLite-база текущей схемы явно подготавливается при сборке. Runtime-пользователь может изменять файл и создавать необходимые журналы. В новом контейнере нет демонстрационных типов встреч и бронирований.
- [ ] Обычный запуск проверяет существующий файл БД. Отсутствующее, недоступное, повреждённое или неподдерживаемое хранилище останавливает запуск без создания замены.
- [ ] Через интерфейс контейнера проходит сценарий «создать тип встречи → бронирование гостем → список владельца календаря». Другая попытка на пересекающийся интервал отклоняется; повтор той же попытки сохраняет прежнее поведение.
- [ ] Новый отдельный контейнер из того же образа без постоянного тома начинает с пустых списков. Контейнер с явно подготовленным постоянным локальным хранилищем сохраняет тип встречи и бронирование после перезапуска и пересоздания; пересборка не заменяет постоянный файл.
- [ ] Документация содержит воспроизводимые сборку, запуск с PORT и использование постоянного локального хранилища. Описано различие между новым пустым контейнером и повторным подключением прежней БД.
- [ ] Контракт, схема БД, правила доступности и существующая цепочка генерации сохраняются. Защищённый workflow Hexlet не изменён, новых тестов нет, существующий полный `mise run check` проходит.
- [ ] Отчёт связывает commit и идентификатор образа с командами и результатами локальной внешней приёмки, включая PORT, маршруты, пустое состояние, постоянное хранилище и отказ при непригодной БД. Результат обозначен как локальная готовность без утверждения о состоявшемся публичном деплое.

## Testing Decisions

Применяются T1–T6 и локальная часть T9 спецификации #55. Используется существующий полный `mise run check`; образ отдельно проверяется снаружи через браузер и HTTP с настоящим backend и SQLite. Существующие локальные Playwright fixtures не считаются проверкой production-контейнера. Проверки постоянного и непригодного хранилища выполняются на изолированных одноразовых данных, без обращения к рабочей БД разработчика. Новые тесты, случаи и тестовая инфраструктура не добавляются.

## Blocked by

None (can start immediately).

## Scope and handoff

Покрывает AC1–AC5, локальные части AC9–AC10, AC11, AC13–AC14 родителя. Подключение Render и создание публичного ресурса выполняются отдельными задачами. Push, PR и merge требуют отдельных явных команд по workflow проекта; локальная готовность этой задачи сама по себе их не разрешает.
