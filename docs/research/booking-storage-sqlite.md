# SQLite для основной записи на встречу

Исследовано 2026-11-09 для [исследовательского вопроса](https://github.com/skaffman41/ai-for-developers-project-386/issues/35). Это проверка кандидата; окончательный выбор остаётся в [вопросе хранения](https://github.com/skaffman41/ai-for-developers-project-386/issues/31). Производственный код, зависимости и тесты не менялись.

## Вывод о применимости

**SQLite со встроенным `node:sqlite` подходит для согласованного одного экземпляра backend. Необходимости в `better-sqlite3` исследование не выявило.** Минимальный обоснованный вариант: одно соединение `DatabaseSync`, один постоянный локальный файл, `BEGIN IMMEDIATE` перед проверкой и записью, общий журнал окончательных результатов попыток, `journal_mode=DELETE` и `synchronous=EXTRA`. На macOS — также `fullfsync=ON`.

Это вывод из документированных гарантий и разовых наблюдений ниже, а не обещание производительности. В точном Node.js 24.22.2 API имеет статус **Stability 1.2 — Release candidate**, а не Stable. Принятие этого статуса и синхронного доступа — явные условия выбора. Альтернатива `WAL + FULL` также обеспечивает нужную долговечность, но для единственного синхронного соединения не требуется ради исключения пересечений.

Входные требования: один backend без горизонтального масштабирования; сохранность при перезапуске, аварийном завершении процесса и перезагрузке сервера с исправным постоянным диском; результаты попыток без автоматического истечения. Утрата диска и автоматические резервные копии вне охвата. [Источник требований](https://github.com/skaffman41/ai-for-developers-project-386/issues/35).

## Документированные факты о точной версии

| Аспект       | Подтверждение                                                                                                                                       |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Статус API   | В tagged-документации **v24.22.2** указан Release candidate; переход отмечен с v24.15.0. Импорт `node:sqlite` доступен без `--experimental-sqlite`. |
| ESM          | Документация показывает `import { DatabaseSync } from 'node:sqlite'`; модуль доступен только с префиксом `node:`.                                   |
| Синхронность | Методы `DatabaseSync` выполняются синхронно. Есть SQL через `exec`, подготовленные выражения и привязка параметров.                                 |
| Управление   | Есть `timeout`, `isTransaction` и файловый путь; ограничения внешних ключей включены по умолчанию.                                                  |

Это сведения из [документации Node.js v24.22.2](https://github.com/nodejs/node/blob/v24.22.2/doc/api/sqlite.md), а не из текущей документации другой major-версии.

Исходник той же версии открывает файл через `sqlite3_open_v2`; обычное соединение использует `READWRITE | CREATE`. `timeout` передаётся в `sqlite3_busy_timeout`; `isTransaction` проверяет `sqlite3_get_autocommit`. Ошибки SQLite представлены как `ERR_SQLITE_ERROR` с числовым расширенным `errcode` и строкой `errstr`. [Исходник v24.22.2](https://github.com/nodejs/node/blob/v24.22.2/src/node_sqlite.cc#L229).

Официальная матрица v24.22.2 относит **macOS arm64 ≥13.5** и **Linux x64 с kernel ≥4.18, glibc ≥2.28** к Tier 1. Это не распространяет подтверждение автоматически на Alpine/musl: такой Linux x64 указан как Experimental. [Матрица платформ](https://github.com/nodejs/node/blob/v24.22.2/BUILDING.md#platform-list).

В окружении проекта проверен именно `v24.22.2`, `darwin arm64`, встроенный SQLite **3.53.4**. Установленный `@types/node` **24.19.2** объявляет `node:sqlite`, `DatabaseSync`, `timeout`, `isTransaction`. Разовый `.mts` успешно проверен TypeScript **6.0.3** с `NodeNext`, `strict`, `target ES2023` и выполнен самим Node. Это локальное наблюдение; пометка `@experimental` в декларациях не заменяет статус из tagged-документации runtime. Обновлять зависимости для этого не понадобилось.

Синхронное чтение, ожидание блокировки и сброс на диск занимают вызывающий поток. **Вывод для приложения:** операции хранения должны быть короткими; внутри транзакции нельзя делать сетевые запросы или `await`. Один синхронный блок на основном потоке не допускает перемежения обработчиков между проверкой и записью, но блокирует обслуживание других запросов на это время. Нагрузочная приемлемость не измерялась. Вынос в Worker не является условием текущего решения и не добавляется этим исследованием.

`better-sqlite3` также предлагает синхронный API, транзакции и Worker support; это внешний native addon с отдельной установкой и готовыми бинарными сборками для основных платформ. Сам по себе он не убирает блокировку вызывающего потока и не усиливает гарантии SQLite. [Документация владельца библиотеки](https://github.com/WiseLibs/better-sqlite3#readme). Точная версия и установка этого драйвера не проверялись: требуемые операции доступны во встроенном.

## Транзакция подтверждения и повторов

**Документированные факты.** SQLite допускает только одну одновременную пишущую транзакцию. `BEGIN IMMEDIATE` запрашивает её сразу и может вернуть `SQLITE_BUSY`; чтение до получения этой транзакции не является защитой от гонки. [Управление транзакциями](https://www.sqlite.org/lang_transaction.html#deferred_immediate_and_exclusive_transactions). Отдельные соединения не видят частичные незакоммиченные записи; сериализация достигается последовательным выполнением записей. Операции одного соединения не изолированы друг от друга. [Изоляция](https://www.sqlite.org/isolation.html).

**Предлагаемый протокол — вывод для принятых гарантий:**

1. У каждой попытки есть собственный устойчивый идентификатор и неизменяемые нормализованные отправленные данные. Email, имя, тип и время сами по себе не являются ключом попытки. Отдельные формы могут создавать независимые попытки с одинаковыми данными.
2. Начать `BEGIN IMMEDIATE`. После получения блокировки найти сохранённый результат по идентификатору. Если он есть, сверить данные и вернуть исходный результат после завершения транзакции. Успешную старую попытку не проверять заново на прошедшее время или занятость её собственным бронированием.
3. Если результата нет, заново прочитать тип встречи, вычислить окончание и проверить действующие правила доступности, текущее время и пересечение полного интервала. Всё это происходит под той же пишущей транзакцией.
4. При успехе вставить бронирование и окончательный результат попытки в **одной транзакции одного файла**. Сохранить достаточно данных для восстановления исходного подтверждения.
5. При окончательном бизнес-отказе записать его результат для этой попытки в той же транзакции, без бронирования. После сохранённого отказа эта попытка больше не переоценивается и не превращается в успех.
6. Выполнить `COMMIT`. Успех или окончательный отказ сообщать только после подтверждённого сохранения соответствующего результата. Потеря ответа после успешного commit не отменяет запись: повтор находит её.

Атомарность нескольких записей в одной транзакции — свойство SQLite; выбор состава этих записей и порядок действий выше — проектный вывод. [Атомарный commit](https://www.sqlite.org/atomiccommit.html#introduction). Обновлять бронирование и результат в разных транзакциях нельзя: иначе после сбоя возможны бронирование без ответа попытки либо ответ без бронирования.

Для принимаемой сервером идентифицированной попытки сохраняются **успехи и сообщаемые окончательные отказы без TTL**. Техническая ошибка не записывается как постоянный бизнес-отказ. Отсутствие результата после завершённого отката позволяет повтору той же попытки снова проверить актуальную доступность. Эти правила следуют из [согласованных гарантий](https://github.com/skaffman41/ai-for-developers-project-386/issues/28#issuecomment-6734724429), а не возникают автоматически от SQLite.

Тот же протокол нужен для **создания типа встречи**: отдельное пространство идентификаторов операции либо ключ, включающий вид операции; проверка исходных данных; создание типа и сохранение результата одной транзакцией; повтор возвращает тот же тип. Совпадение названия не является дублем. Конкретные поля ключа, формат повторяемого результата и реакция на использование ключа с другими данными остаются вопросом API. [Требование повтора создания](https://github.com/skaffman41/ai-for-developers-project-386/issues/30#issuecomment-6736579601).

Ограничения `PRIMARY KEY`/`UNIQUE` полезны для идентификатора попытки и связи «не более одного бронирования на попытку»; ключевые поля должны быть `NOT NULL`. `CHECK(end > start)` проверяет корректность одной записи. SQLite не разрешает подзапросы в `CHECK`, поэтому такой CHECK не исключит пересечения с другими строками. [Ограничения таблиц](https://www.sqlite.org/lang_createtable.html#check_constraints). Полную схему этот документ не утверждает.

## Полные интервалы и общая занятость

**Математический вывод:** два непустых полуоткрытых интервала `[existing_start, existing_end)` и `[requested_start, requested_end)` пересекаются тогда и только тогда, когда:

```sql
SELECT 1
FROM bookings
WHERE starts_at < :requested_end
  AND ends_at > :requested_start
LIMIT 1;
```

Параметры передаются привязкой, а не подстановкой строк. Запрос не фильтруется по типу встречи и выполняется после `BEGIN IMMEDIATE`, перед вставкой. Начало и окончание должны иметь единое сравнимое представление, например целое число миллисекунд UTC; правила рабочего дня применяются в `Europe/Moscow`. Не следует сравнивать локализованные строки дат.

| Уже сохранено | Новая попытка            | Результат проверки       |
| ------------- | ------------------------ | ------------------------ |
| 09:00–10:30   | 10:00–10:30 другого типа | Пересечение              |
| 09:00–10:30   | 09:30–11:00              | Пересечение              |
| 09:00–10:30   | 10:30–11:00              | Разрешено: соприкасаются |

Уникальность начала или пары «тип + начало» не решает задачу. При последовательных пишущих транзакциях вторая независимая попытка увидит commit первой до своей проверки. Гарантия действует при соблюдении протокола **всеми путями записи**. Для будущих дополнительных путей можно рассмотреть trigger с тем же условием и `RAISE`; [SQLite поддерживает такие triggers](https://www.sqlite.org/lang_createtrigger.html#the_raise_function). Это возможная защита схемы, а не дополнительная обязательная инфраструктура текущего решения.

## Busy, ошибки commit и неизвестный исход

**Документированные факты.** `COMMIT` может вернуть `SQLITE_BUSY`, оставив транзакцию активной; его можно повторить после освобождения читателя. Некоторые ошибки могут автоматически откатить всю транзакцию. [Поведение транзакций при ошибках](https://www.sqlite.org/lang_transaction.html#response_to_errors_within_a_transaction). `sqlite3_get_autocommit` позволяет определить, продолжается ли транзакция; в Node это `isTransaction`. [Проверка autocommit](https://www.sqlite.org/c3ref/get_autocommit.html). Busy timeout ограничивает ожидание блокировки и затем возвращает busy; он не гарантирует успех. [Busy timeout](https://www.sqlite.org/c3ref/busy_timeout.html).

**Предлагаемое поведение приложения:**

| Ситуация                                                      | Действие и наблюдаемый результат                                                                                                                                                                                                  |
| ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Busy на `BEGIN IMMEDIATE`                                     | Ограниченный повтор либо технический ответ с возможностью повтора той же попытки. Не «Слот уже занят».                                                                                                                            |
| Busy на `COMMIT`, транзакция активна                          | Можно повторить сам commit; при исчерпании политики ожидания откатить. Не запускать тело операции второй раз внутри активной транзакции.                                                                                          |
| Ошибка записи, диска, I/O или commit                          | Проверить `isTransaction`; при активной транзакции попытаться откатить. Если откат/соединение ненадёжны — прекратить его использование. Не утверждать окончательный отказ по одному исключению.                                   |
| Ответ потерян либо commit не удалось надёжно классифицировать | Сохранить неизвестный исход для клиента; после восстановления доступа прочитать результат той же попытки из исправного соединения. Если результата нет и предыдущая транзакция завершена, повтор может выполнить протокол заново. |
| Результат отказа не удалось сохранить                         | Не сообщать устойчивый окончательный отказ: следующий повтор ещё может успешно создать бронирование.                                                                                                                              |

Числовой primary code можно получить как `errcode & 0xff`: старшие биты описывают расширенную причину. `BUSY` — 5, `LOCKED` — 6, `IOERR` — 10, `FULL` — 13. Нельзя классифицировать занятость календаря по тексту исключения SQLite. [Коды SQLite](https://www.sqlite.org/rescode.html). `isTransaction=false` само по себе не различает успешный commit и автоматический rollback: нужен результат операции либо чтение сохранённого исхода.

Если повтор commit откладывается асинхронно, всё соединение должно оставаться недоступным другим операциям до завершения транзакции. Минимальный вариант с одним синхронным блоком может вместо этого выполнить ограниченное ожидание SQLite, затем rollback и вернуть неизвестный исход. Длительное синхронное ожидание задержит весь backend; конкретный timeout здесь не выбирается.

## Долговечность и файлы

**Документированные факты о настройках.** В `DELETE` значение `EXTRA` синхронизирует также каталог после удаления журнала: обычный `FULL` может потерять последний commit при потере питания. В WAL режим `FULL` обеспечивает долговечность, `NORMAL` допускает потерю подтверждённых транзакций после сбоя ОС. `fullfsync=ON` включает поддерживаемый macOS `F_FULLFSYNC`. Неизвестные PRAGMA игнорируются. [Документация PRAGMA](https://www.sqlite.org/pragma.html#pragma_synchronous).

**Рекомендация для текущего объёма:** перед обслуживанием запросов явно установить и прочитать обратно `journal_mode=DELETE`, `synchronous=EXTRA`, `foreign_keys=ON` и ограниченный `busy_timeout`; на macOS — `fullfsync=ON`. Проверять результат, а не только отсутствие исключения. Настройки соединения применять при каждом открытии; изменение journal mode выполнять вне транзакции. Это не переход к новому режиму журнала при каждом запросе.

WAL остаётся альтернативой: `journal_mode=WAL`, `synchronous=FULL`. Он допускает параллельных читателей при одном writer, использует `-wal`/`-shm` и checkpoint; commit уже может находиться в WAL до переноса в основной файл. WAL не работает через сетевую файловую систему. [Механика WAL](https://www.sqlite.org/wal.html). Для одного соединения дополнительная параллельность чтения не используется.

Атомарность и долговечность предполагают корректные блокировки и исполнение flush/fsync операционной системой, файловой системой и накопителем. SQLite не может компенсировать ложный ответ оборудования об успешной синхронизации. [Предположения SQLite](https://www.sqlite.org/atomiccommit.html#hardware_assumptions).

**Условия эксплуатации, выведенные для этих гарантий:**

- Один явно заданный постоянный локальный путь, одинаковый после перезапуска и пересборки. Не `:memory:`, не временный каталог, не каталог сборки и не исчезающий слой контейнера. Точный каталог и способ конфигурации ещё не выбраны.
- Процессу доступны сам файл и его каталог для записи журнала. Родительский каталог находится на том же исправном постоянном хранилище. Смена CWD не должна незаметно создавать другую базу по относительному пути.
- Файл базы и `-journal`, а при WAL также `-wal`/`-shm`, управляются SQLite. Нельзя удалять, переименовывать или терять журнал для восстановления после аварии. Сетевое хранилище с ненадёжными locks и ручная замена открытого файла не входят в обоснованный вариант. [Условия повреждения и восстановления](https://www.sqlite.org/howtocorrupt.html).
- Штатное закрытие соединения полезно, но не является условием сохранности уже подтверждённого commit. Утрата самого диска этой схемой не покрывается; резервное копирование не добавляется данным решением.

## Пустая инициализация и версия схемы

**Документированные факты.** SQLite хранит `user_version` для приложения и отдельно собственную версию схемы. `application_id` может отличать формат приложения. Журнал содержит часть состояния, необходимую для аварийного восстановления. [Формат файла](https://www.sqlite.org/fileformat2.html#user_version_number). SQLite сам не реализует политику миграций приложения.

**Минимальная безопасная политика запуска — предложение:**

1. Проверить выбранное расположение хранилища и открыть файл до начала обслуживания HTTP. Нельзя подменять ошибку доступа созданием памяти или пустой базы в другом месте.
2. Для явно разрешённого первого запуска создать пустую схему в `BEGIN IMMEDIATE`, записать её версию и commit. Не добавлять демонстрационные типы и бронирования. Версия `0` допустима для инициализации только у действительно пустой базы, без чужих объектов.
3. Для известной текущей версии проверить ожидаемую структуру. `CREATE TABLE IF NOT EXISTS` само по себе не подтверждает совместимость существующей таблицы.
4. Если понадобится переход с известной старой версии, выполнять только предусмотренное преобразование, DDL и обновление `user_version` одной транзакцией; при ошибке откатить и не начинать обслуживание. Полный migration framework сейчас не требуется.
5. Неизвестная/более новая версия, чужая непустая база, несовместимая схема, повреждённый или недоступный файл останавливают запуск с понятной диагностикой. Нельзя автоматически удалять файл, сбрасывать версию, «чинить» неизвестную схему или создавать пустую замену.

Отсутствие файла при первом разрешённом запуске отличается от ошибки открытия. Если ожидается уже существующее хранилище, его исчезновение должно останавливать запуск; автоматическое создание SQLite не может определить, что оператор потерял прежний volume. Как различать первичное создание и ожидаемый существующий файл, следует закрепить в контракте запуска, без добавления сервиса хранения.
